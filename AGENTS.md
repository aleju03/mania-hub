# Repository Guidelines

## What This Is

Mania Hub (mania-tracker.com) is an osu!mania community site with two cooperating parts:

- A TanStack Start + Vite React 19 app in `src/`, SSR via Nitro (node-server preset, self-hosted on the VPS; Vercel is only a rollback build target).
- An always-on live backend in `live-backend/` that listens to Kayla's oSC score feed, keeps durable SQLite projections warm, runs a DB-backed job queue, and streams updates to the frontend over SSE.

Surfaces: rankings (country + global), live tracker, top plays, maps, snipes, farm helper, replay viewer with video export, player profiles (about, recent, activity, maniacard), personal goals, a My Data dashboard, card packs (collectible maniacards), a BBCode profile editor, settings, and admin dashboards. An optional Discord bot (maniabot) adds a dev-gated `/discord` showcase and `/admin/discord` controls.

Countries are dynamic. The backend keeps a `country_registry` with per-country status (cold -> warm -> active, pausable) and a feature tier (`indexed`, `maps_warm`, `live`, `snipes`) that gates which projections run. Visiting a cold country can activate it (rate-limited). A synthetic `GLOBAL` scope aggregates all tracked countries. Default/home country is `CR`.

## Development Commands

The user often keeps local servers running; do not start dev servers or builds unprompted. If asked: frontend is `3000`, live backend is `7227`.

- Frontend dev: `npm run dev`. Build: `npm run build`. Tests: `npm run test`. Typecheck: `npx tsc --noEmit`.
- Single test: `npx vitest run path/to/file.test.ts` (add `-t "name"` for one case).
- Live backend dev: `cd live-backend && npm run dev`. Tests: `npm test`. Typecheck: `npx tsc --noEmit`. Tests + build: `npm run verify`.
- oSC smoke: `cd live-backend && npm run smoke:osc`.
- Backend DB compaction: `cd live-backend && npm run compact:storage` (full VACUUM/GC) or `npm run compact:maps-farmed` (rebuild maps-farmed overlay).
- Sync prod DB to local: `npm run live-db:update` creates a fresh VPS snapshot (`VACUUM INTO` + zstd), downloads it, replaces the local SQLite DB, and prunes old remote `online-*` snapshots (keeps 2, `--keep-remote N`). `npm run live-db:sync-from-vps` reuses the newest pre-existing backup instead; supports `--dry-run`/`--force`, plus `--backup-local` (keeps `--keep-local N` copies of the replaced local DB, default 2). Run these from a dev PC, never on the VPS: they overwrite the local DB.
- Dan tooling: `npm run dan:benchmark`, `npm run dan:analyze`.

## Live Backend Architecture

The live backend is the source of truth for live surfaces when `VITE_LIVE_BACKEND_URL` is configured. Browsers fetch a snapshot on page entry, then subscribe to SSE for deltas. SSE is one-way backend-to-browser; users never connect to oSC directly.

Ingest flow:

1. Scores arrive from three sources: the oSC Socket.IO feed (real-time), oSC JSON backfill (catch-up after downtime), and an osu! API recent-scores fallback poller (safety net, own rate bucket).
2. Scores are filtered to mania. Country detection uses `country_rosters` plus enriched user data, because oSC payloads do not include country.
3. Raw rows land in `score_events`; user/beatmap/beatmapset metadata is upserted; projections and follow-up jobs fan out according to the country's feature tier.
4. The backend emits SSE events (`tracker_score`, `top_play`, `snipe`, `maps_farmed_update`, `goal_completed`, `job_status`, `status`, `replay_video_export`), plus a `hello` event on connect and `heartbeat` keepalives. Reconnecting clients replay missed events via `Last-Event-ID` against `live_event_log`. Two high-volume types are stored as a reference rather than a payload (`compactLiveEventPayload` in `live/event-log.ts`): a `tracker_score` keeps its score identity and a `pack_pull` its event id, and both rehydrate from their durable table on replay, so the log does not carry a second copy of data it can look up.

Rosters are warmed from osu! mania performance rankings on a schedule; roster refreshes also capture `country_rank_snapshots` used for 7-day rank deltas.

## Queue and Jobs

The queue lives in the `jobs` table with priority, dedupe keys, and per-type backoff. Under load it sheds pressure: low-priority job types are auto-deferred (`deferred_pressure`) when queue depth is high and wake when it drains. Workers run in dedicated lanes (fast enrichment, osc-backfill, osc-country-catchup, maps-refresh, dan-estimates, activity-analysis, chart-analysis, snipe-seed, replay-video render and finalize).

Job types:

- `enrich_user`, `enrich_beatmap`: fetch full metadata from the osu! API.
- `refresh_country_roster`: refresh a country's roster and rank snapshots from osu! rankings.
- `refresh_user_top_scores`: confirm a candidate top play and compute PP gain.
- `refresh_profile_user`, `refresh_profile_snapshot`: catch a viewed profile up off the request path (osu! user payload; full user + best-200 re-mint). Both are queued by the profile endpoints, never awaited by them.
- `reconcile_user_recent_scores`: sync a user's recent scores from the osu! API to fill ingest gaps.
- `refresh_user_maps_farmed_scores`, `refresh_country_maps`, `refresh_global_maps`: maps-farmed aggregation per user, per country, and globally.
- `refresh_qualified_maps`: hourly qualified-maps watch; pulls osu!'s current qualified mania list in one search call and reconciles `/maps` status (promote pending->qualified, index new sets, resolve ranks/dequalifies).
- `seed_snipe_board`: build the initial board for a beatmap/lane.
- `analyze_activity_beatmap`: compute skill vectors for player activity.
- `analyze_beatmap_chart`: unified chart analysis per beatmap at 1.0x (classifier dan verdict, pattern clusters, MinaCalc MSD skillsets) into `beatmap_chart_analysis`.
- `recompute_vibro_sweep`, `recompute_dan_floor_pin_sweep`, `recompute_ln_subtype_sweep`: one-shot boot-seeded sweeps over stored chart analyses (gated by `live_meta` done-keys), patching detector/classifier changes into the corpus without a full `CHART_ANALYSIS_VERSION` re-run.
- `compute_dan_estimate`: dan rating for a beatmap at a rate.
- `compute_player_skills`: Etterna-style skillset ratings from a player's top plays into `player_skill_ratings`.
- `osc_backfill`, `osc_country_catchup`: oSC JSON catch-up, global and country-scoped.
- `replay_video_server_render`, `replay_video_export`: server-side render and finalization/upload.

## Feature Models

### Snipes
Each beatmap/lane has a stored board in `country_beatmap_scores` (keyed by country + beatmap + lane + user), so raw scores do not have to be kept forever. A new score is compared to that board; when it overtakes someone the backend writes `snipe_events` and emits an SSE `snipe`. If no board exists yet, `seed_snipe_board` fetches roster users' scores for that beatmap and builds it.

That board is readable at `/api/snapshots/snipe-board?country=XX&beatmap=<id>&mods=DT,HD&lazer=1` (lane derived server-side from the mods and client, so callers pass what a snipe event already carries; ordered by total score, `limit` caps at 100 and the response still reports the full `total`). The frontend loads it lazily when a `/snipes` row is expanded.

### Top plays
Detected country top plays live in `top_play_events`. When an incoming score is near the player's known top-play threshold, the backend queues `refresh_user_top_scores`, confirms via the osu! API whether it actually entered the player's top plays (confirmation window ~30min), records the PP gain, then emits `top_play`.

### Maps
`refresh_user_maps_farmed_scores` pulls a roster user's top 200 and extracts scores that entered their top plays; `refresh_country_maps` aggregates these into `country_maps_snapshots`, and `refresh_global_maps` rolls countries up into a global snapshot. Refresh progress is tracked in `live_meta` and surfaced via `/api/snapshots/maps-progress`.

The `/maps` browser reads from `map_search_index` (materialized from `beatmap_skill_vectors` + beatmap/set metadata). Status stays fresh via the zero-API reconciler in `map-search.ts` (`buildMapStatusPropagationStatement` / `reconcileMapSearchIndexStatuses`), event-driven plus hourly, which only upgrades in-flux -> settled to shield against stale score payloads; and the hourly `refresh_qualified_maps` watch (`features/qualified-maps-watch.ts`), which is the one writer allowed to move a row backwards (qualified -> pending on a dequalify) because the osu! API read is current truth. The watch writes status into `metadata_json.$.status` + the status column (via `persistScoresDisplayMetadata`) and the index, filters to native mania diffs (skips converts), and enqueues `analyze_beatmap_chart` for newly-qualified diffs so they become searchable. `SOURCE_SELECT` excludes sub-0.2* in-flux placeholder diffs (empty stubs that ride along in pack and loved sets), and `pruneMapSearchPlaceholderRows` clears any already indexed.

Free-text search terms of 3+ characters route through `map_search_fts`, an external-content FTS5 trigram table over `search_text` (created and trigger-synced in `db.ts`; same `%term%` semantics as the LIKE they replace). Shorter terms stay on LIKE (lone ASCII characters are dropped as noise), result counts stop at `MAP_SEARCH_COUNT_CAP` (5000, shown as "5,000+"), offsets past the cap short-circuit, and `/api/snapshots/maps-search` sits on the `publicCostly` rate bucket behind a 30s prepared-response cache (`searchResponses` in `maps-response-cache.ts`).

### Farm helper
Recommends maps by comparing the subject player's top 200 against a global peer pool at similar PP, using candidates from `country_maps_farmed_scores` across all countries. Per-keymode (4k/7k) weighted PP lives in `farm_helper_user_key_stats`, seeded on first access.

`country_maps_farmed_scores` carries write-time lane columns (`key_count`, `speed_bucket`, `mods_key`; -1/null = unknown, readers fall back) so the peer aggregation filters by keymode in SQL and never re-derives mods per row; the whole cohort read stays inside the covering index `idx_country_maps_farmed_scores_user_lane`. A one-time boot backfill (`farmed_scores_lane_backfill:v1` in `live_meta`) populated existing rows. The A8 accuracy benchmark scale floors at 0.5, and gain-view snapshots report `belowGainFloorCount` (lanes dropped only by the 1pp minimum-gain floor) so `/farm-helper` can explain an empty board and point at the popular view.

### Activity
Per-day player skill vectors (stream, jack, bracket, LN variants and friends) in `player_activity_*` tables, computed by `analyze_activity_beatmap` jobs. The analysis is versioned (`ACTIVITY_SKILL_ANALYSIS_VERSION`) for cache invalidation.

### Dan estimates
`dan_estimates` caches ratings keyed by a cache version from `live-backend/src/dan/`. Small batches are computed inline at request time; larger requests queue `compute_dan_estimate`. Since cache version 7 the estimates come from the unified chart classifier (`live-backend/src/dan/chart-classifier.ts`, routing 4K RC to LeoBlack Mixed, 4K LN to the in-house kNN, 6K/7K through Sunny interval tables), so 6K and 7K charts are supported.

### Chart analysis
`beatmap_chart_analysis` stores, per beatmap at 1.0x and keyed by `CHART_ANALYSIS_VERSION`, the lean classifier verdict + pattern clusters (`classification_json`) and MinaCalc MSD skillsets (`msd_json`), plus extracted columns (`key_count`, `primary_label`, `primary_family`, `raw_dan`, `msd_overall`) for SQL consumers. Jobs enqueue alongside activity skill analysis for every newly seen beatmap; `POST /api/admin/chart-analysis/backfill?limit=N` sweeps already-cached `.osu` files with no row at the current version (no osu! API cost). The admin page's one-click run (`/api/admin/chart-analysis/{start,cancel}`) drives a self-chaining runner that keeps the analysis queue topped up until the whole cache is covered; pace is set by `CHART_ANALYSIS_LANE_INTERVAL_MS` (default 500ms per chart). Chart analysis runs even when `ENABLE_OSU_API_JOBS` is off (it only skips the `.osu` network fallback then). A backfill computed on one machine can seed another DB: `npm run export:chart-analysis` -> gzip/scp -> `npm run import:chart-analysis:dist -- <file>` (idempotent, existing rows win, schedules a full map search index rebuild afterwards).

The LeoBlack engines and MinaCalc wasm live in `live-backend/vendor/leoblack` (a copy of `src/lib/leoblack`; keep the two trees plus the facade ports in `live-backend/src/dan/` in sync when the frontend classifier changes).

### Profiles and rankings
`player-profiles.ts` caches a best-200 snapshot for 24h (projected forward by top-play events) and profile sections (about, recent) for ~2 minutes. Opening a profile serves the stored snapshot and queues its osu! work (`refresh_profile_user`, `refresh_profile_snapshot`); the only osu! call left on the request path is minting a player never stored at all, which is what a search for an untracked player does.

Presence follows from that: the green dot means a tracked play inside the 10-minute session window and nothing else (osu!'s own `is_online` is ignored here since it also counts idling and browsing; the rankings list still shows it, from a live call, on purpose). Last seen is the newest of the last tracked play and the payload's `last_visit` while that payload is inside its refresh TTL; neither available means no last-seen line at all.

`global-rankings.ts` serves a snapshot built from the union of every tracked country's roster (`country_rosters` joined with `users`, limited to tracked, ranked members with non-null pp), ordered by mania pp, with 7-day deltas from `rank-snapshots.ts`. A `pool=packs` query variant merges manual roster opt-ins (rank null, `source = 'manual'`) into that board by pp, so a self-added player is a pullable maniacard while staying off every leaderboard; pack-pool reads also skip the stat-repair enqueue. Adding `keys=4` or `keys=7` narrows the packs pool to players whose main keymode that is (higher variant pp from `users.pp_4k`/`pp_7k`, falling back to per-keymode farmed weighted pp from `farm_helper_user_key_stats`; players with no signal are in neither) - this backs the 4K/7K card packs, and a failed keymode build fails the request rather than serving the unfiltered pool.

### Goals
Logged-in players set targets stored in `user_goals` (kinds `reach_pp`, `play_pp`, `play_pp_count`, `accuracy`, `pass`, `grade`, `fc`, `reach_rank`), always owned by the osu!-verified viewer id. Play-shaped goals auto-complete the moment ingest sees a matching play (`evaluateScoreGoals`, guarded so a goals bug cannot drop a score); total-pp goals settle on top-play confirmation (`evaluatePpGoals`) and reconcile lazily on read. A `live_meta` marker (`user_goals_changed_at`) plus a negative cache keep the ingest hot path cheap. Completion emits SSE `goal_completed`. Served by `/api/goals`, `/api/goals/create`, `/api/goals/delete`; frontend route `/goals`.

### My Data
`my-data.ts` powers a signed-in player's personal dashboard (frontend route `/my-data`) and adds no table of its own. `getMyDataSummary` aggregates stats that are not on an osu! profile (personal records, a country-timezone-bucketed play-rhythm clock, a mods fingerprint, key/card/goal counts) behind a 30s per-user cache; `getUserTrackedFeed` is a user-scoped tracker feed over `player_activity_score_refs` joined to `score_events`; `getUserTopPlaysFeed` reads the player's durable `top_play_events`. Endpoints `/api/my-data/{summary,dashboard,feed,top-plays,skills}`.

`player-skills.ts` backs the dashboard's "Skill rating" card: per-play MinaCalc SSRs over the player's cached top plays, computed at the play's music rate (DT/NC 1.5x, HT/DC 0.75x, custom `speed_change` skipped) with the play's accuracy as the score goal, aggregated per keymode with Etterna's erfc aggregation into `player_skill_ratings` (keyed by `PLAYER_SKILLS_VERSION`; per-play SSRs cached in `plays_json` so recomputes only run the calc for new plays). Each mode also carries per-pattern ratings over the charts' chart-analysis pattern tags (min 3 plays per tag): the 4K card shows native MSD skillsets plus the LN pattern axis, 6K/7K show pattern axes only, since MinaCalc's skillset names are 4K vocabulary. Converts (non-Mode-3 `.osu`) and non-4/6/7K charts are skipped. `getPlayerSkillBreakdown` enqueues `compute_player_skills` when the row is missing, older than 12h, has pending plays after 30min, or a newer `top_play_events` row landed; like chart analysis it runs with `ENABLE_OSU_API_JOBS` off.

### Card packs
`pack-wallets.ts` persists the maniacard "pack" economy behind `/packs`. `pack_wallets` holds per-user economy state (shards, charges, opened packs) behind a `rev` optimistic-concurrency guard (`savePackWallet`), plus `owner_username`, the durable name fallback for collectors with no `users` row; `pack_collection_cards` holds owned player cards, imported out of legacy card blobs and stripped from the stored payload. An ownership row carries only what belongs to that holding (tier, copies, recycle balance, pull stamps, current pp/rank, and a `skills_id`): the card's identity (name, avatar, country, tier label) is one row per variant in `pack_cards`, and the mint's skills snapshot is interned in `pack_card_skills` (one row per distinct snapshot, referenced by id). Snapshots are frozen per owner and immutable, so sharing a row between collectors who minted the same numbers is safe; identity is first-write-wins so a forged sync cannot repaint a card other collectors hold. `ensurePackCardCatalog` (a boot write in `server.ts`) rebuilds a pre-split database once, preserving every owner's own snapshot. Unreferenced `pack_card_skills` rows are not swept today (~45k rows / ~9MB across the feature's life). Recycling mints shards by tier value, with every copy past the first paying `DUPLICATE_RECYCLE_RATE` (half, floored at one shard); that discount is what keeps packs a purchase rather than an income source. `src/lib/pack-collection.ts` mirrors this table on the frontend, and the SQL forms are generated from the tables rather than hand-written so they cannot drift. Endpoints: `/api/packs/warm`, `/api/packs/cards?ids=`, `/api/pack-wallet/{id}` (GET/POST, 4MB body limit), `/api/pack-collection/{id}` (GET list, POST recycle, POST `mode: "mint"` to persist a re-minted card's skills snapshot, the only way a client can repair a card collected before skills snapshots existed).

The pack card view (`GET /api/profiles/{user}/cached-snapshot?view=card`, `/api/packs/cards?ids=` for a whole hand) is served by `getCachedPackCardSnapshots` in `player-profiles.ts`, reading `profile_snapshots` (falling back to `users` + `user_top_scores`) straight to what a maniacard renders. It deliberately does not go through `getCachedPlayerProfileSnapshot`, whose presence, projected pp, per-score users and beatmapset covers the card throws away. It does keep `applyPackCardScoreOverlays`: top-play events and tracked plays newer than the stored snapshot, batched for the whole hand with each player's own cutoff, because a stored window is ~12 days old on average and a card minted without it under-rates the player permanently. Both reads run on `ctx.db`, never `serveWriteDb`.

`pack-pulls.ts` is the community layer: `pack_pull_events` is an append-only, client-reported pull log (never economy) powering the `/packs` community-pulls strip, per-card ownership counts and "your card got pulled" stats. Endpoints: `POST /api/packs/pulls`, `GET /api/packs/pulled-by/{id}`, plus public `GET /api/packs/card-stats?ids=`, `/api/packs/pulled-stats/{id}`, `/api/packs/recent-pulls`, `/api/packs/pulled-card/{owner}/{card}` (the durable share payload behind `/pull/{owner}/{card}` and its `kind=pull` OG image). Retention: ordinary events 14d, notable 365d. Nothing durable reads an ordinary event past that: the hourly pull cap looks back an hour, the "got pulled" count 7 days, and first-global is answered by `pack_card_serials` (durable) rather than by scanning the log.

`pulled-by` is the named form of the `pulled-stats` count: `getPackCardCollectors` lists who holds one player's card, oldest holding first, folding an owner's ordinary card and GOAT into one entry at the better tier. The list is deliberately not public, only the count is: `fetchServerPackCardCollectors` resolves the card id from the osu! login cookie so you can only list collectors of your own card, and it is **admin-gated while it is prototyped** (`requireAdminAccess` on the server fn, `canUseAdminFeatures` on the `/packs` trigger). `src/components/packs/CardCollectors.tsx` renders it as one wrapped run of names in mint order with a pinned footer for the hovered collector and a name filter past 24.

`pack_card_serials` is the mint registry the pull log writes alongside each event: one row per (card key, owner), holding the serial that owner pulled the card at, where #1 is the first collector anywhere. The number is computed inside the insert (so two pulls cannot claim the same serial) and never renumbered, so it survives duplicates, recycling and pull-event retention. Only signed-in pulls are logged. Existing collections were seeded once by `backfillPackCardSerials` (a boot write in `server.ts`) from `pack_collection_cards.first_pulled_at`; it only numbers owners with no serial yet and starts after that card's current max, so a rerun can only append. Serials surface on the `/pull` share payload, on synced collection rows, and in the `POST /api/packs/pulls` response (`mints`).

`pack-duels.ts` is the head-to-head layer, also **admin-gated while it is prototyped** (`requireAdminAccess` in `src/lib/pack-duels.ts`, `canUseAdminFeatures` on `/duel/{id}` and the `/packs` entry point). `pack_duels` holds one row per duel. A duel is top trumps played for keeps: the challenger stakes the hand from a pack they opened, whoever opens the link answers by opening a real pack of the same type (`/packs?duel={id}`, reusing the packs page's wallet, charge, reveal and pull log) and stakes that, and the two hands play `TRUMPS_ROUNDS` rounds of one card each. Both sides attack every round, simultaneously and blind, with one stat off their own card (`control`, `speed`, `precision`, `stars`); an attack lands when your card is strictly higher on the stat you chose, so a round is worth up to two points and neither seat gains from acting last. Each stat can be spent only once per duel and there is exactly one round per stat, so the decision is which card spends your Speed; `redactDuelFor` reveals a pick once its round is over, so spent stats are public. Most landed attacks wins, tiebroken on total power of cards played; rounds are capped at the shorter hand.

Because cards actually move, a hand is not taken on trust the way the pull log is: `holdsWholeStake` checks every staked card against `pack_collection_cards` before a duel can open or be answered (all or nothing), and on resolve `transferPackCollectionCards` moves one copy of each of the loser's staked cards to the winner, writing the receipt to `spoils_json`. A card recycled between staking and losing moves as its shard value instead. Serials do not travel: `pack_card_serials` records who pulled a card, and a won card was not pulled. A tie moves nothing. Card stats stay client-reported, which only bends who wins a round. `picks_json` is an append-only pick log (a write guards on `picks_count` so simultaneous attacks cannot overwrite each other or settle twice, and the read path re-enforces one pick per round and one use per stat). Endpoints: `POST /api/packs/duels`, `POST /api/packs/duels/{id}/{join,pick,view}`, public `GET /api/packs/duels/{id}` (every unplayed card hidden). `ensurePackDuelsSchema` (a boot write) adds pick/payout/spoils columns to a database that met an earlier prototype. Dev-only self-duel hatch: the backend accepts a join from the challenger when `nodeEnv !== "production"` and the page shows the seat button under `import.meta.env.DEV`; both gates are independent and neither exists in a production build.

The solo game lives inside `/packs` at `?view=streak` (`src/components/packs/StreakGame.tsx`; `/streak` only redirects there, since old links are out in the world). It is hosted rather than standalone so the pull ticker, charge dots and shard count stay on screen; the collection panel hides while it is open. Unlike duels it is open to everyone. Rounds ask about play count or ranked score (`STREAK_METRICS`, rotated per round), not pp: those are wide-range numbers printed nowhere on a card and decoupled from rank, which is why both cards show rank and pp on purpose. Right answer deals a new card, wrong answer ends the run, and "cash out" banks the streak (before it existed, leaving mid-run dropped everything, since the claim only fired on a wrong guess). The draw is pure and tested in `src/lib/streak-game.ts`: three pool depths via `streakPoolDepth` (`top500` = 500, the default; `top` = `STREAK_POOL_PLAYERS` 1000, kept under that name so best streaks stored before the third depth existed still mean what they meant; `anyone` = the whole snapshot) of tracked global rankings, loaded a page at a time, nobody repeated within a run, players missing the metric skipped, dead-even pairs given to the player. Hard mode (`StreakPool` `"anyone"`, locked mid-streak) aims at a uniformly random pool position and fetches the page holding it (`streakRankPage`/`streakPageSlice`), because drawing from loaded pages would favour the top; both modes share loaded pages, with `streakPoolEntries` keeping deep pages out of the top-1000 game. Best streaks live in `localStorage` per pool (`mania-hub-streak-best-v1`, `mania-hub-streak-best-anyone-v1`, `mania-hub-streak-best-top500-v1`). It spends no osu! API budget: card art comes from `fetchCachedPackPlayerScores` only, and an unknown player plays as an avatar tile and is warmed in the background.

Blitz is the same game dealt by the backend (`live-backend/src/features/pack-streak.ts`, table `pack_streak_runs`), because a leaderboard cannot be fed by a client-reported streak. The server picks both players and the question, keeps the face-down card's number in `round_json`, and counts a guess only if it arrived before `deadline_at` (`STREAK_ROUND_MS` 12s, plus `STREAK_ROUND_GRACE_MS` 1.5s for the wire; a follow-up round is dealt with `STREAK_REVEAL_HOLD_MS` added so the reveal animation does not eat the clock). Run endpoints are server-to-server (`POST /api/packs/games/streak/{start,guess,cashout}`, wrapped by `src/lib/streak-blitz.ts`); the board is public (`GET /api/packs/games/streak/board?pool=&me=`, `StreakLeaderboard.tsx`, top 10 plus the viewer's own rank, one board per pool (three), ties broken by who got there first). It reads `pack_streak_bests` (one row per account per pool, upserted by `endRun` only when a run beats that account's own record) rather than grouping over the run log, which is what lets `pack_streak_runs` stay transient: ended runs drop `seen_json` and are pruned after `BLITZ_STREAK_RUN_LOG_RETENTION_DAYS` (45), keeping `guess_ms_json` until then. The records themselves are durable and never pruned; the only thing that takes one off the board is a true admin removing it, done from the board itself (a per-row control in `StreakLeaderboard.tsx` that only renders for `auth.isAdmin`, calling `removeLiveStreakBest` -> `POST /api/admin/packs/streak/remove`, which deletes the record plus that account's ended runs in the pool and leaves a live run alone). Removal is deliberately not a ban: the account can set a new record immediately, and nothing remembers the old one. There is no admin page for this on purpose, since the board is the place it is read. `sweepAbandonedStreakRuns` runs hourly from `retention.ts` and closes (and pays) runs more than 10 minutes past their deadline, since a run only reaches the board by ending. Starting a run closes and pays any run the account left hanging, so an account has one live run and abandoning is never worth more than stopping; blitz payouts happen inside `endRun` off the server's streak, so the client never claims one. Requires a sign-in (a board is a list of accounts). What the clock buys is the end of alt-tabbing to a profile mid-round, not unscriptability: the rankings and per-player numbers are public API on the same backend, which is what `guess_ms_json` (per-guess response times) is kept for.

`pack-games.ts` is the arcade's till, shared by both games. Duels pay on resolve (`DUEL_WIN_SHARDS` / `DUEL_TIE_SHARDS` / `DUEL_LOSS_SHARDS`, written to `challenger_shards`/`opponent_shards` so a player returning to the link still sees what they earned). A finished streak run is claimed via `POST /api/packs/games/streak` (`streakShardReward` = `STREAK_SHARDS_PER_CORRECT` (8) per correct guess plus a growing bonus at every fifth in a row, so one long run pays more than two short ones). Every payout goes through `grantPackGameShards`, which trims it to what is left of `GAME_SHARD_DAILY_CAP` for the day (UTC), books it in `pack_game_rewards` and adds it via the same `addWalletShards` recycling uses. The cap is the security model for the two client-scored modes: a casual streak is scored in the browser off public data and two accounts can always trade duel wins, so no amount of server-side state makes either unfarmable; the cap is set below what idling on `/packs` already earns uncapped (a charge every 30s, 2 shards an open, ~240/hour). Blitz runs are the exception and are paid from the server's own count (see `pack-streak.ts`), though they draw on the same daily cap and ledger. `POST /api/packs/games/allowance` is the read the streak page uses for what is left today.

### GOAT nomination poll (temporary)
`live-backend/src/features/goat-poll.ts` backs a time-boxed community poll on `/packs` for who should join the honorary GOAT roster (`src/lib/honorary-players.ts`). Signed-in users nominate a player and vote nominees up or down; net score (`up - down`) is public and is what the board sorts on, so the ranking is the community's and no hide/reject decision sits with one person. When the window closes the owner reads the board and edits `HONORARY_PLAYERS` by hand — nothing here promotes anyone by code.

Banned and deleted accounts are first-class nominees, since a third of the existing roster is exactly that and osu!'s `/search` cannot return a restricted user. Those come in through a manual path that demands a `web.archive.org` snapshot of the osu! profile; `normalizeArchiveProof` validates it and pulls the osu! user id out of the archived URL, which is what stops two spellings of a deleted player's name opening two rows and splitting the vote. Dedupe is two unique indexes on `goat_poll_nominees`: `(poll_id, name_key)` always, plus a partial `(poll_id, osu_user_id)` where an id is known.

Neither nominating nor voting is capped. These endpoints take the admin-token bridge and so bypass the per-IP abuse guard, which leaves the ceilings structural rather than numeric: an osu! login behind every write, the unique indexes that keep one player to one row, the `(poll_id, nominee_id, voter_user_id)` primary key on `goat_poll_votes` that makes one voice per account per nominee, and admin removal (`POST /api/admin/goat-poll/remove`) for a board that grows junk. A vote cap never limited write volume anyway (clearing and re-voting is unbounded), and a 3-nomination cap had people out of nominations within the first hour of the first poll. A vote is `+1`/`-1`; clearing deletes the row. Nominating casts the nominator's own upvote, so a new row opens at net 1. Every write publishes a country-less `goat_poll` SSE event carrying the one changed row (or `removedId`), so open boards patch themselves instead of waiting on their 20s poll. Alt accounts are the residual hole and are accepted: the result is read by eye, not taken mechanically.

The whole switch is the `GOAT_POLL` constant at the top of `features/goat-poll.ts` — `enabled`, `id`, `opensAt`, `closesAt`. Deliberately code, not env: a poll's dates are a product decision rather than a secret or a per-deployment setting, so starting, stopping or rerunning one is a push from this repo instead of an SSH session editing `.env` on the VPS, and git history records when each poll ran. `enabled: false` retires it (every route 404s and the widget hides); `adminOnly: true` keeps it running but unreleased — the board read requires the bridge token (so admins reach it through `fetchGoatPollBoardAsAdmin` in `src/lib/goat-poll.ts` rather than browser-direct) and writes are refused unless the frontend forwards `viewerIsAdmin`, read off the same verified login cookie that supplies `userId`. The refusal is the retired-poll 404, not a 401, so an unreleased poll is indistinguishable from one that does not exist. The shared token cannot carry this on its own: every signed-in user's bridged calls have it. `id` scopes the rows so a rerun starts clean while the old board stays queryable; the window is the only source of truth for the deadline (the browser renders whatever `GET /api/goat-poll` returns and every write re-checks it server-side), and `opensAt` is what the progress pie fills against so it is correct for a poll of any length. Both dates must be written as explicit UTC instants (`YYYY-MM-DDTHH:MM:SSZ`): `Date.parse` would also accept a Z-less or space-separated string and read it as *local* time on whichever machine parsed it, so one committed config would mean different moments on the VPS and on a laptop. An unparseable, inverted, timezone-less or impossible date (V8 rolls `02-31` into March rather than rejecting it, so the parse is round-tripped) switches the poll off rather than opening one that never closes. The board also carries `serverNow`, the backend's clock at the moment it answered: the widget counts down against `Date.now() + (serverNow - receivedAt)` instead of its own clock, so a viewer whose machine is set to the wrong day still sees the deadline that their vote will actually be checked against. There is deliberately no second switch on the frontend. Both tables are excluded from retention: the board is the record.

Endpoints: public `GET /api/goat-poll` (board, browser-direct — it refreshes on a timer in every open packs tab and carries no per-viewer data), plus `LIVE_ADMIN_TOKEN`-bridged `GET /api/goat-poll/mine?userId=`, `POST /api/goat-poll/vote`, `POST /api/goat-poll/nominate` (wrapped by `src/lib/goat-poll.ts`, which also rejects anyone already on the honorary roster), and two true-admin-only routes under `/api/admin/goat-poll/`: `remove` and `voters`. Writes publish a `goat_poll` SSE event (see above), so `LIVE_EVENT_NAMES` in `src/lib/live-backend.ts` must carry that name or follower tabs miss it. A retired poll 404s the board read, which the frontend distinguishes from a network failure (`GOAT_POLL_OFF`) and then stops polling — otherwise a dead poll costs every open packs tab a 404 every 20s forever.

`GET /api/admin/goat-poll/voters?nomineeId=` is the ballot behind one row: who voted, which way, and when. Deliberately not on the public board — a poll that names your downvotes is a poll people vote on differently — but the person who has to decide what the result meant cannot otherwise tell `+8` built out of one player's friends from `+8` the community agreed on. Voter names come from the `users` projection, then from `analytics_viewers` (`AnalyticsStore.getViewerNames`, the other database, best effort) for anyone off the tracked rosters, then not at all: a bare id is still a voter, and no osu! API call is spent on this. The frontend side is `fetchGoatPollVoters` behind `requireTrueAdminAccess`, and the widget's row is only clickable when `auth.isAdmin` — the same narrower flag that gates removal, not the wider dev-access one that decides who can *see* an unreleased poll.

### Discord bot
`live-backend/src/discord/` is an HTTP-interactions bot (maniabot): slash commands with autocomplete, message components, per-channel subscription feeds (top plays, snipes, new farm maps), and osu! account linking. Feeds post only from the serving process via `app.events.subscribe(app.discord.feedSink)` (`server.ts`). Gated by `ENABLE_DISCORD_BOT` (default off) and `ENABLE_DISCORD_FEEDS` (default on), with `DISCORD_*` config in `config.ts`. HTTP: `/api/discord/interactions` (Ed25519 signature-verified, ahead of the public rate gate), `/api/discord/info` (public, cached 60s), and `/api/admin/discord/{status,register-commands,register-emojis,guilds,remove-subscription}`. Frontend: `/discord` and `/admin/discord`.

Replies are Components V2 (`components.ts` converts the embed shape into containers/sections/galleries at the REST layer) and lean on custom application emojis for grade pills and mod icons (`emojis.ts`). The PNGs are built from the in-app SVGs by `scripts/build-discord-emojis.mjs` into `public/images/discord/emojis/`, uploaded once via the admin "Register emojis" action (name->id map in `discord_emojis`), and referenced inline as `<:name:id>`. Every render helper falls back to plain text when an emoji is not registered. Keep embeds free of decorative unicode emoji (enforced by `discord-embeds.test.ts`); custom-emoji references are ASCII and exempt.

### Discord server directory (`/communities`)

A directory of osu!mania Discord servers, posted by the people who run them. `live-backend/src/features/communities.ts` + `http/routes/communities.ts`, table `discord_communities` (migrated in `db.ts`, not `001_initial.sql`), frontend `src/routes/communities.tsx` + `src/lib/communities.ts`.

Two things carry the trust, and neither is the form. The submitter proves through Discord's own OAuth (`identify` + `guilds`, `src/lib/discord-auth-server.ts`) that they own or hold Manage Server on the guild, re-derived server-side on submit rather than trusted from the picker. And the listing's identity - name, icon, banner, member and online counts - comes from Discord's unauthenticated invite endpoint (`live-backend/src/discord/invites.ts`, standalone so it works with `ENABLE_DISCORD_BOT=false`), which also refuses an invite pointing at a different guild than the one proved. No Discord token is stored: it lives in a 30-minute signed cookie bound to the osu! account that connected it, and is revoked once a listing is in.

Nothing publishes on submit. A row is born `pending` and a moderator approves it at `/communities/review`; an owner's later edit goes live immediately but raises `edited_since_review`, which is the second list on that page.

Reviewing is deliberately **not** an `/admin` surface. `COMMUNITY_MODERATOR_USER_IDS` in `src/lib/communities-shared.ts` is a hand-kept list (the same shape as `SKIN_KEYMODE_MODERATOR_USER_IDS`), the queue is reached from a button on the directory itself, and the review server functions re-check `canModerateCommunities` rather than `requireTrueAdminAccess` - so trusting somebody with servers implies nothing else on the site. The backend review routes live under `/api/communities/` for the same reason, and carry the moderator's osu! id so every decision is attributable in the logs. A rejected listing that its owner edits goes back to pending. `communities/refresh.ts` re-resolves every approved invite on a 6-hour sweep (started beside retention, since it spends no osu! API budget), refreshing counts and dropping a listing off the directory after `COMMUNITY_INVITE_FAIL_LIMIT` consecutive failures; a Discord outage (`lookup_failed`) deliberately does not count. The owner still sees a hidden listing, with a warning, and one good check restores it.

The form is checked as it is filled in rather than on submit: `POST /api/communities/preview` re-resolves the pasted invite against Discord and answers with the real server (name, icon, banner, counts) or the same refusal code submit would give, so a mismatched or already-listed link is caught before a description is written and an expiring one is warned about. Called with an empty invite and a guild id it tries to find one instead, via `fetchWidgetInviteCode`: an OAuth app cannot create an invite (that is a bot action inside the server, and `identify` + `guilds` grants nothing like it), but a server with its widget on publishes a permanent one at an unauthenticated `widget.json`, so those fill themselves in. What it finds still goes through `resolveDiscordInvite`, so a widget invite is checked exactly like a pasted one; `no_auto_invite` means the field has to ask. It writes nothing, and 200s with `ok:false` for a refusal because "that invite expires" is an answer, not a failed request. The modal renders `CommunityCard` beside the form as a live preview, so the card being posted is the card that will appear.

Tags are owner-typed, up to five, stored as a JSON array in `tags_json` and normalized by `normalizeTags` (lowercase, no quotes or wildcards in the charset, deduped, capped) - which is what lets the tag filter match `like '%"<tag>"%'` without half-matching a longer tag. There is deliberately **no vocabulary**: a fixed list of keymodes and purposes was tried and dropped before the directory opened (a list of Discord servers has no business asking about keys), and those columns were removed. Every filter row - country, language, tags - is built from facets the list query returns (tags via `json_each`), counted over the search but *before* the country/language/tag filters apply, so the page only ever offers values with servers behind them, switching between them always stays possible, and a row hides itself until there is more than one thing to choose between. An expiring invite is deliberately allowed rather than refused: it is a worse listing, not an invalid one, and the refresh sweep already retires a listing whose link stops resolving. The expiry is stored in `invite_expires_at`, warned about in the form, and shown on the owner's own row and on the review card, so it is visible while it can still be fixed. Descriptions run to 1000 characters and keep their line breaks (`cleanPitch`, rendered `whitespace-pre-line`, folded past ~200 chars on the card).

A listing may name **who it is for**: `access_scopes_json` holds country codes and the `R-` region codes from `regions.ts` mixed freely, empty meaning everyone, and `access_hidden` is the owner's second choice - whether someone outside those places sees the listing with no way in, or does not see it at all. Enforcement is in `toCommunitySummary`, not in the UI: a viewer who does not match gets `inviteUrl: null` and no `guildId`, plus a `guildCreatedAt` decoded from the snowflake so the page keeps its date. So a restricted invite is not in the markup, on a hover or in a network tab. The art is kept rather than dropped, because a locked card is meant to show whose server it is: `iconUrl`/`bannerUrl` point at the frontend's `/api/community-image?id=&kind=` for those viewers instead of at Discord's CDN, whose paths carry the guild id (and `widget.json` turns a guild id into an invite for any server with its widget on). That route re-reads the osu!-verified viewer, re-checks the early-access gate, asks the backend's `GET /api/communities/image-url` (which 404s unless `communityVisibleTo` says this viewer may see the listing at all, so the page and its pictures cannot drift), then fetches the CDN image and pipes back only the bytes: `private, max-age=3600`, content type checked against an allowlist, capped at 4 MiB, and refusing any source URL that is not `cdn.discordapp.com`. The viewer's country comes off the osu!-verified profile and is forwarded over the admin-token bridge; a browser cannot assert it. The hidden kind is filtered in `listCommunities` above the facet cut (so totals and the country facet agree) and 404s on `/get`. Note this filters, it does not enforce: anyone already inside can paste the invite anywhere, and a real wall is Discord-side membership screening.

Anyone browsing can **flag** a listing from its page (`POST /api/communities/report`, table `discord_community_reports`), which is what watches a listing after approval. A report is a message to the moderators: the owner never sees one, no count shows on a card, and `viewerReported` on `/get` tells only the person asking that theirs is standing. A unique index on `(community_id, reporter_user_id)` keeps one person to one report (sending another rewrites theirs and reopens it), and `COMMUNITY_MAX_OPEN_REPORTS_PER_USER` is what stops one account flagging the whole directory. Reports ride along on `/api/communities/queue` as a third list plus a by-listing map, so a flagged listing is on the review page once with its reports under it; any decision on it - including approving, which is how a moderator says "looks fine" - resolves them, and deleting the listing deletes them.

**Gated while it is tried out**: `canUseCommunities` in `src/lib/communities-shared.ts` limits it to a true admin plus `COMMUNITIES_EARLY_ACCESS_USER_IDS`. Deliberately not `canUseDevFeatures`, which is only honoured on localhost and `ninja.mania-tracker.com`; this is checked against the signed-in osu! id so an early tester can use the real site without getting every other dev-gated page. Because of the gate there is no anonymous read path yet: every read is a server function and the backend routes are all behind the admin-token bridge. Opening it up means adding a public list route plus a direct fetcher, relaxing the gate, dropping `noindex`, and adding `/communities` to the sitemap.

## Admin Surfaces

Admin controls are exposed through the frontend at `/admin/live-backend` and backend `/api/admin/*` (status, ingest fixtures, roster refresh, pause/resume country, set status/tier, delete country). Be careful with destructive controls.

### Ghost overlay
`/admin/ghost` is the owner's ghost overlay: a Deltarune sprite driven around a visitor's screen, able to speak in a typewriter bubble, hold a pose, and run one-shot actions. It is page-scoped, and the audience is everyone on that route, one signed-in viewer picked off the presence roster, or nobody; the owner always sees his own ghost. The control stage frames the real page in an iframe at the watched viewer's viewport size, and the framed copy stays asleep via a `#ghost-preview` hash so it neither joins the roster nor draws a second sprite. Backend state is `live-backend/src/live/ghost.ts` (`GhostHub`, in-memory, serving process only, nothing durable, gated by `ENABLE_GHOST`); the visitor overlay is `src/components/ghost/`, mounted once from `__root.tsx`.

- Characters (Ralsei, Starwalker, Annoying Dog) are defined in `GHOST_CHARACTERS` in `src/lib/ghost-shared.ts`, the only place a new one has to be added: atlas, frame size, feet anchor, clip table, per-clip pixel bounds (hitbox and bubble lift come off the drawing, not the mostly-transparent frame), walk mapping, poses, actions, size range. Size on the wire is raw sprite pixels, so ranges differ per character and the backend clamps to 1..12. Unknown character ids and unknown clip names resolve to that character's default rather than a missing atlas row.
- Atlas URLs carry a per-character `atlas.version` because the service worker caches `/images/*` forever; tests pin each file's hash and grid, so changing art without bumping the version fails.
- The Starwalker and dog atlases are packed by `scripts/dev/pack-ghost-atlas.py`, a by-hand dev script needing Pillow and a local DELTARUNE install. Its header is the record of which sprites and frames each row came from and of the sheet-damage repairs; read it there rather than duplicating it here.
- Endpoints (deliberately bland `updates` paths on the wire: nothing a visitor's devtools shows may read like spying or hint the overlay exists): `GET /api/updates/stream?route=` (public SSE, one per page open, own budget via `GHOST_MAX_CLIENTS` / `GHOST_MAX_CLIENTS_PER_IP`, never the live-feed one; also the presence roster), `POST /api/updates/ticket` (admin-token gated, `getGhostControlTicket` in `src/lib/ghost.ts`), `POST /api/updates/control?ticket=` (driven from the browser at ~15 Hz so movement never pays for a hop through the frontend server), `GET /api/updates/presence?ticket=` (per-route counts capped at 40 routes, identities for signed-in viewers capped at 120), `POST /api/updates/say` (viewer replies, connection id from their own `hello` event, 6 per 30s, control characters stripped so a reply cannot forge an SSE frame), `GET /api/updates/inbox?ticket=` (replies, 40-entry in-memory ring, never SQLite).
- Viewer identity is a frontend-signed HMAC of `ghost:<id>:<username>:<expiry>` keyed with `LIVE_ADMIN_TOKEN` (`getGhostViewerTicket`), so aiming at one person cannot be spoofed via query string; an unsigned connection is anonymous and only ever sees an everyone-audience ghost.
- Route folding (lowercased pathname, no query or hash, no trailing slash, optional `/*` section wildcard) is duplicated on both sides and held together by tests. Broadcasts index clients by route, so a 15 Hz tick on an exact route only touches that page's connections.
- A line and an action stay on the session until replaced, so a late arrival still reads the current bubble; the overlay remembers what it has already shown a visitor (keyed by id and content) so a reload does not re-type a read bubble or re-fire the last action. Ending is ordered: `op: "end"` queues behind in-flight control patches (a patch overtaking its end would silently recreate the session), a disconnect with no route closes every session at once, and the hub sweeps idle sessions on a 10-minute window even with the panel gone.

### Admin todos
`/admin/todos` is the owner's private todo list, backed by `features/admin-todos.ts` (durable `admin_todos` table, single user, no per-user scoping) over `GET /api/admin/todos` + `POST /api/admin/todos/{create,update,delete,clear-done}`. Frontend server fns in `src/lib/admin-todos.ts` proxy with the shared admin token; the nav entry and page are `canUseAdminFeatures`-gated.

### Analytics
`live-backend/src/features/analytics.ts` is the site's only analytics store; there is no third-party fallback. The frontend `/api/sync` proxy writes every tracked event to `POST /api/analytics/capture` (bearer-token gated, stamped with the edge GeoIP country and a bot verdict). Events land in a separate SQLite file (`ANALYTICS_DATABASE_URL`, default `data/mania-hub-analytics.db`, own WAL) through a 1s-batched writer; retention self-prunes hourly (`ANALYTICS_RETENTION_DAYS`, default 90). Both admin surfaces require `LIVE_BACKEND_URL` + `LIVE_ADMIN_TOKEN`. Read side:

- `GET /api/admin/analytics/monitor`: the `/admin/live-backend` analytics tab, polled at 5s (KPIs, a 48-bucket traffic timeline, the recent-event feed, aggregate cards).
- `GET /api/admin/analytics/viewers`: the signed-in roster, backed by the durable `analytics_viewers` table, which is upserted on flush and survives event pruning so it answers "who has ever signed in". `?sort=recent|pp|rank` orders it; pp/rank are read out of the main DB's `users` table per viewer id (`features/analytics-viewer-ranks.ts`) since the two live in separate SQLite files, and that sort scans the whole roster before slicing to `limit` so the top is the real top. A viewer the backend has never ingested comes back `pp: null` and sorts last. `?country=XX` filters in SQL, so a country's page reaches players older than an unfiltered page's cut; the response carries `matched` plus `countries` for the filter's own list.
- `GET /api/admin/analytics/viewer-events?viewerId=`: one player's trail, fetched only when a roster row is expanded, off a partial expression index on the events table's `viewer_id` prop, newest first, bots and the player's own `/admin/` browsing excluded. The roster is durable and events are not, so an empty answer means retention rather than failure.
- `GET /api/admin/analytics/valley`: the `/valley` villager layer.
- `GET /api/admin/analytics/live`: realtime SSE, authenticated by short-lived tickets from `POST /api/admin/analytics/live-ticket`.

## HTTP Surface

`/healthz` and `/readyz` are open, and are what a liveness or uptime probe should use. `/api/status` is **not** public: it needs `LIVE_ADMIN_TOKEN` like `/api/admin/status` (it is the same body without the worker-activity extras), because queue pressure, DB headroom, the osu! API budget and the abuse counters together describe exactly when the backend is least able to absorb load. Public endpoints: `/api/countries/features`, `/api/countries/activate`, `/api/snapshots/*` (tracker, top-plays, snipes, snipe-board, maps, maps-page, maps-progress, maps-set, maps-players, rankings, global-rankings, farm-helper, farm-helper-farmers, rank-deltas), `/api/profiles/{user}/{section}` (snapshot, cached-snapshot, about, recent, activity, activity-day, activity-availability), `/api/dan-estimates`, `/api/audio`, `/api/hitsounds`, `/api/storyboard` (zip of the set's root .osb plus referenced images for the replay viewer; empty zip means no storyboard, cached in R2 including negatives), `/api/packs/{warm,cards,card-stats,pulled-stats/{id},recent-pulls,duels/{id}}`, `/api/goat-poll`, `/api/events` (country-activating event-log replay since `?since=`), `/api/discord/info`, `/api/replay-video-job`, the SSE stream at `/api/live?country=XX`, the ghost stream at `/api/updates/stream?route=` (public because every page open holds one; identity optional and signed), and the replay-viewer presence stream at `/api/replay/presence?key=score:<id>|upload:<id>`. `/api/discord/interactions` is public but Ed25519 signature-verified, ahead of the public rate gate.

Replay presence emits SSE `count` events for the viewer's "Spectators (N)" counter: in-memory refcounts, anonymous by default, `observe=1` receives counts without being counted (admin viewers). A watcher who enabled "show my name under spectators" adds `uid`/`name`/`exp`/`sig`, an HMAC of `spectator:<id>:<username>:<expiry>` keyed with `LIVE_ADMIN_TOKEN` and minted by `getReplaySpectatorTicket` in `src/lib/replay-spectator.ts`; their username joins a `names` array, deduped per account and capped.

A class of per-user endpoints is gated by `LIVE_ADMIN_TOKEN` but lives outside `/api/admin/*`: the frontend server fn injects the shared token plus the osu!-verified viewer id, so a user only ever touches their own data. These are goals (`/api/goals`, `/api/goals/create`, `/api/goals/delete`), my-data (`/api/my-data/{summary,dashboard,feed,top-plays,skills}`), roster self opt-in/out (`/api/roster/self-add`, `/api/roster/self-remove`), pack wallet/collection/pull-log (`/api/pack-wallet/{id}`, `/api/pack-collection/{id}`, `/api/packs/pulls`, `/api/packs/pulled-by/{id}`), duels (`POST /api/packs/duels`, `/api/packs/duels/{id}/{join,pick,view}`) arcade payouts (`/api/packs/games/{streak,allowance}`) and the GOAT poll's write side (`/api/goat-poll/{mine,vote,nominate}`). The osu! API proxies `/api/osu/v2` and `/api/osu/beatmap-file` are also `LIVE_ADMIN_TOKEN`-gated and called server-to-server, not from browsers.

All public endpoints are rate-limited per IP by `abuse-guard.ts` with separate buckets (general, costly, pack hands, dan estimates, country activation with per-IP/global/new-country sub-limits, SSE connections with per-IP and total caps, replay video jobs). Note the general bucket applies to every `/api/` path, so a route with its own bucket spends both. CORS allows origins from `ALLOWED_ORIGINS`. `/api/admin/*` requires `LIVE_ADMIN_TOKEN`.

## Replay Video Export

The whole feature is gated by `ENABLE_REPLAY_VIDEO` (default `false`; on only in the owner's local env). When off, `/api/replay-video-job` returns 404, the replay-video worker lanes are not registered, and playwright-core is never imported (it is a dynamic import inside the render function).

Two paths, both finishing in the backend queue:

1. Browser render: WebCodecs encodes the MP4 client-side, then the frontend calls `/api/replay-video-job` (`start` -> `upload-video` -> `finish`).
2. Server render: the backend queues `replay_video_server_render`, which drives headless Chrome (playwright-core) against the frontend to render the video.

Either way, `replay_video_export` finalizes: optional ffmpeg audio mux and optimization, upload to R2 (or local path), status in `replay_video_exports`, polled by the frontend via `action=status`. `scripts/dev/replay-video-job.ts` is a local Vite middleware fallback when no live backend URL is configured.

## Retention and Storage

The backend uses LibSQL/SQLite (default `live-backend/data/mania-hub-live.db`, WAL mode); `DATABASE_URL` may point to a file or remote. `live-backend/src/retention.ts` runs hourly. Defaults (configurable): `score_events` 14d, `live_event_log` 7d, done `jobs` 2d, `api_call_log` 7d, finished `replay_video_exports` 2d plus temp dir cleanup, rank snapshots 14d, player activity 2y. Two further tables are pruned on fixed (non-configurable) cutoffs every tick: `beatmap_osu_files` 90d and `discord_channel_map_context` 30d. The DB size is capped (~10GB max; over the cap triggers compaction toward ~8GB).

Durable projections (`country_beatmap_scores`, `snipe_events`, `top_play_events`, `user_top_scores`, maps snapshots, users, beatmaps, beatmapsets, rosters) are not part of the short raw-event cleanup.

Caching lives where each resource lives. osu! API responses: cached in the backend's `/api/osu/v2` proxy (`osu_proxy_cache` table, `features/osu-proxy-cache.ts`), opt-in per call via `cacheTtlMs`/`staleMs` on `osuFetch`; the proxy also collapses concurrent identical fetches in-process and serves expired rows through upstream failures within `staleMs`. Computed artifacts (parsed replays, uploaded-replay descriptions): gzipped JSON objects in R2 via `getJsonArtifact`/`putJsonArtifact`. The `getPersistentCache*`/`fetchWithCacheLock` helpers in `src/lib/api.ts` kept their signatures but are a per-instance memory tier plus in-flight dedup only; there is no shared frontend KV. R2 objects are managed by `src/lib/r2-cache.ts`; size is bounded by per-prefix Cloudflare lifecycle rules, never by code. Two buckets exist: the private `mania-hub-replay-cache` (roots `replay-cache/` and `skins/`) and the public CDN bucket `mania-hub-public` behind cdn.mania-tracker.com (roots `bbcode/` and `maniacards/`, written by `public-image-store.ts` / `pack-thumbnail-store.ts`). `/admin/r2` browses both through the `ADMIN_BUCKETS` registry in `r2-cache.ts`, which is the only place a browsable root or its delete warning is declared; a new top-level prefix stays invisible to the admin browser until it is listed there.

## Frontend Data Rules

Prefer `src/lib/live-backend.ts` for live backend calls from client routes: typed snapshot fetchers, `openLiveEventSource()` for SSE, and the country feature-tier bootstrap. Home, Tracker, Top Plays, Snipes, and Maps hard-require the live backend (no `VITE_LIVE_BACKEND_URL` renders a `LiveBackendRequired` notice; the osu!-API fallback scans were deleted). Server functions remain only for data the backend does not project: user profiles/scores, rank histories, per-beatmap country scoreboards (replay browse), beatmap search/files, dan estimates, OG cards. When an SSE connection drops, the browser's `EventSource` reconnects and replays missed events via `Last-Event-ID` against `live_event_log`; there is no polling fallback (`/api/sync` is unrelated, it is the analytics capture proxy). The live stream is also shared across tabs (`src/lib/cross-tab-event-source.ts`): tabs elect a leader per stream URL via the Web Locks API, the leader holds the one real `EventSource` and relays events over a `BroadcastChannel`, and on leader death the lock passes to another tab, which resumes gap-free through the backend's `?lastEventId=` replay. A visible follower that hears no relay for 45s (a leader tab suspended by the browser keeps the lock but relays nothing) quietly opens its own direct connection and drops it when the relay resumes. The relay forwards the event names in `LIVE_EVENT_NAMES` (`src/lib/live-backend.ts`) — a new SSE event type must be added there or follower tabs will never see it.

Keep authenticated osu! API access on the server. Do not put osu! credentials or direct authenticated osu! calls in client components. `src/lib/osu.ts` is a facade over domain modules in `src/lib/osu/`.

Client state uses Zustand in `src/store.ts`, persisted to localStorage under `mania-hub-cache-v5`; bump the version on breaking shape changes. Data is country-keyed with `fetchedAt` plus TTL checks from `src/lib/cache.ts`. Persistence is debounced with quota-eviction handling; critical preferences (theme, hidden users, avatar accents) live in separate storage keys so they survive quota errors. Check `useHasHydrated()` before trusting persisted state during SSR hydration.

OG images are rendered by `src/routes/api/og.ts` (@vercel/og) and cached in R2 keyed by the `OG_IMAGE_VERSION` constant in `src/lib/seo.ts`; bump it there when changing OG layouts. Meta and OG URL builders also live in `src/lib/seo.ts`; the sitemap is `src/routes/api/sitemap.ts`.

## Coding Style

Use TypeScript, React function components, two-space indentation, semicolons, and named exports where local style uses them. Prefer existing helpers and patterns over parallel abstractions.

Use `#/*` or `@/*` path aliases for imports from `src/*`; match the nearby style. The backend uses relative imports inside `live-backend/src`.

Styling uses Tailwind CSS v4 through `@tailwindcss/vite`, with global styles and theme CSS variables in `src/styles.css`. The theme is hue/saturation custom properties applied before hydration; a custom `hover` variant avoids stuck hover states on touch devices. Animations use `framer-motion`. Replay rendering uses canvas/Pixi modules. 3D card code uses Three.js helpers under `src/components/player/maniacard3d/`.

Replay-related logic is split across parser, validation, score input, skin, navigation, scroll speed, judgement, beatmap parsing, canvas rendering, and video export modules; keep changes scoped to the right module. Stable/lazer score differences matter; use existing score utilities rather than duplicating normalization.

Dan and LN dan classification must stay algorithmic. Do not add title, artist, creator, beatmap ID, beatmapset ID, filename, or chart-specific identity shortcuts to force results.

Backend logs are structured JSON via `live-backend/src/logger.ts` (`logInfo`/`logWarn`); use it instead of `console.log`.

## Testing Guidance

Vitest is the test runner. Tests live beside source files as `*.test.ts` or `*.test.tsx`, plus the `-`-prefixed files at the top of `src/routes/`.

For live backend changes, run at least `cd live-backend && npm test` and `npx tsc --noEmit` (or `npm run verify`). For frontend type-sensitive changes, run `npx tsc --noEmit` at the root.

## Security and Config

Local secrets belong in `.env` and `live-backend/.env`; do not commit secrets.

Important env vars:

- Root/frontend: `VITE_LIVE_BACKEND_URL`, `LIVE_BACKEND_URL`, `LIVE_ADMIN_TOKEN`, R2 vars.
- Live backend (`live-backend/src/config.ts` holds the full ~90-var list with defaults): `PORT`, `DATABASE_URL`, `OSU_CLIENT_ID`, `OSU_CLIENT_SECRET`, `OSC_BASE_URL`, `OSC_SOCKET_PATH`, `TRACKED_COUNTRIES`, `LIVE_PUBLIC_ORIGIN`, `ALLOWED_ORIGINS`, `LIVE_ADMIN_TOKEN`, `LIVE_BACKEND_ROLE` (`all`/`server`/`worker`, alias `BACKEND_ROLE`) for the opt-in two-process split (with `ENABLE_EVENT_LOG_TAIL`, `WORKER_HTTP_PORT`, and `SQLITE_*` connection-pragma tuning), feature flags (`ENABLE_WORKERS`, `ENABLE_OSC_SOCKET`, `ENABLE_OSC_BACKFILL`, `ENABLE_OSU_SCORES_FALLBACK`, `ENABLE_SCHEDULED_REFRESHES`, `ENABLE_GHOST` plus `GHOST_MAX_CLIENTS` / `GHOST_MAX_CLIENTS_PER_IP`), Discord (`ENABLE_DISCORD_BOT`, `ENABLE_DISCORD_FEEDS`, `DISCORD_APPLICATION_ID`, `DISCORD_PUBLIC_KEY`, `DISCORD_BOT_TOKEN`, plus new-farm-map alert thresholds), osu/oSC rate settings, retention settings, roster settings, replay video settings (R2, ffmpeg, Chrome path), analytics settings (`ANALYTICS_DATABASE_URL`, `ANALYTICS_RETENTION_DAYS`).

The live backend defaults to local SQLite at `live-backend/data/mania-hub-live.db`. For production/VPS, configure durable storage and `LIVE_ADMIN_TOKEN`.

The osu! API budget is enforced by a token-bucket client in `live-backend/src/osu/client.ts` (~45/min target, 60/min hard limit), with calls logged to `api_call_log`. Route new osu! API calls through this client. Public backend endpoints are already rate-limited per IP via the abuse guard.
