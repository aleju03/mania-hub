# Feature Models

Deep per-feature reference: snipes, top plays, maps, farm helper, activity, dan estimates, chart analysis, profiles/rankings, goals, my data, uploaded replays, skins. Card packs and the GOAT poll live in `docs/packs.md`; the Discord bot and `/communities` in `docs/discord.md`.

## Tracker

Tracker reads, score hydration and filtering run on a dedicated serving read worker. Country, region and GLOBAL snapshots share a five-second cache and in-flight requests per database, scope, filter and page. Unfiltered totals have a separate five-second cache keyed by predicate, shared across offsets and page sizes; the passed-country index covers country/time/user reads for counting and pagination. GLOBAL HTTP windows align to five-second boundaries for cache reuse. Filtered/star-sorted requests retain the 5,000-row scan cap, so their totals still describe only the scanned matches. SSE continues supplying new scores between snapshot refreshes.

## Snipes

Each beatmap/lane has a stored board in `country_beatmap_scores` (keyed by country + beatmap + lane + user), so raw scores do not have to be kept forever. A new score is compared to that board; when it overtakes someone the backend writes `snipe_events` and emits an SSE `snipe`. If no board exists yet, `seed_snipe_board` fetches roster users' scores for that beatmap and builds it, unless the map's leaderboard opened after `SNIPES_INGEST_SINCE`, in which case the feed already saw every roster play and the board is built from the stored scores alone (see `docs/backend.md`).

That board is readable at `/api/snapshots/snipe-board?country=XX&beatmap=<id>&mods=DT,HD&lazer=1` (lane derived server-side from the mods and client, so callers pass what a snipe event already carries; ordered by total score, `limit` caps at 100 and the response still reports the full `total`). The frontend loads it lazily when a `/snipes` row is expanded.

## Top plays

Detected country top plays live in `top_play_events`. When an incoming score is near the player's known top-play threshold, the backend queues `refresh_user_top_scores`, confirms via the osu! API whether it actually entered the player's top plays (confirmation window ~30min), records the PP gain, then emits `top_play`.

Snapshot reads select the requested page's rowids before loading score payloads. Shallow GLOBAL PP/gain pages first try a bounded prefix of the existing sort index; if that cannot establish a complete page, including boundary ties, the query falls back to the time-window scan. Prepared responses share a five-second cache and in-flight work, keyed by scope, filters, page and encoding; a new event invalidates them immediately.

## Maps

`refresh_user_maps_farmed_scores` pulls a roster user's top 200 and extracts scores that entered their top plays; `refresh_country_maps` aggregates these into `country_maps_snapshots`, and `refresh_global_maps` rolls countries up into a global snapshot. Refresh progress is tracked in `live_meta` and surfaced via `/api/snapshots/maps-progress`.

The `/maps` browser reads from `map_search_index` (materialized from `beatmap_skill_vectors` + beatmap/set metadata). Status stays fresh via the zero-API reconciler in `map-search.ts` (`buildMapStatusPropagationStatement` / `reconcileMapSearchIndexStatuses`), event-driven plus hourly, which only upgrades in-flux -> settled to shield against stale score payloads; and the hourly `refresh_qualified_maps` watch (`features/qualified-maps-watch.ts`), which is the one writer allowed to move a row backwards (qualified -> pending on a dequalify) because the osu! API read is current truth. The watch writes status into `metadata_json.$.status` + the status column (via `persistScoresDisplayMetadata`) and the index, filters to native mania diffs (skips converts), and enqueues `analyze_beatmap_chart` for newly-qualified diffs so they become searchable. `SOURCE_SELECT` excludes sub-0.2* in-flux placeholder diffs (empty stubs that ride along in pack and loved sets), and `pruneMapSearchPlaceholderRows` clears any already indexed. Ranked dates heal on the same hourly tick: a set first seen through a score payload carries osu!'s compact beatmapset (no `ranked_date`) and ingest never overwrites `metadata_json` on conflict, so `reconcileMapSearchIndexRankedDates` copies dates the set row has since gained (or re-stamped: the index follows the set row whenever the two disagree and the set row has one) and `enqueueRankedDateEnrichment` sends sets still dateless on either side to `enrich_beatmap` (one diff per set, 50 sets per tick); that job treats a settled set without a `ranked_date` as never fetched in full regardless of row age, and writes the fresh index row itself. osu! moves `ranked_date` to the ranking (or loved) moment when a qualified set settles, so the Newest sort is meant to surface such a map like a new one rather than leave it a week deep at its qualify date: the propagation flip stamps the index date to now and strips the set row's stale date (guarded on the index still showing the set in flux, so a score on a long-ranked map never triggers a refetch), which routes the set through the enrich job for the real date; the qualified watch and the settled-sets reconcile write the API payload's `ranked_date` alongside the status directly.

Every chart analysis also stores a note-weighted song tempo (`dan/note-bpm.ts`, `classification_json.$.noteBpm`): the median timing-point BPM under the notes' start times, with inflated timing folded back to the song. A section timed above 300 folds when its dominant row gap is coarse (half a beat or more on the inflated grid); above 500 it folds regardless, since no song runs there and 1/4 notes of a 999 grid are 15ms vibro. How far it folds is decided by scoring each candidate divisor's grid on how much of the gap evidence lands on binary snaps (k/16, full weight) or triplet snaps (k/12, half), shallowest wins unless a deeper one clearly explains more; a 999-timed set lands on 249.75, not 333, because 333 would read its 20ms and 40ms rows as 1/9 and 2/9 notes. The value rides in `map_search_index.note_bpm` (copied at upsert) and reaches clients as `noteBpm` on search entries, where the map modal shows it beside the nominal osu! bpm when the two disagree by 3% or more, and as `beatmap.note_bpm` on profile scores for the profile BPM stats. The one-shot `recompute_note_bpm_sweep` re-scans the cached `.osu` corpus once per meta-key version (`note_bpm_recompute_done:vN`), re-visiting only rows a fold-rule change can move, and re-upserts each patched chart's index row.

Free-text search terms of 3+ characters route through `map_search_fts`, an external-content FTS5 trigram table over `search_text` (created and trigger-synced in `db.ts`; same `%term%` semantics as the LIKE they replace). Shorter terms stay on LIKE (lone ASCII characters are dropped as noise), result counts stop at `MAP_SEARCH_COUNT_CAP` (5000, shown as "5,000+"), offsets past the cap short-circuit, and `/api/snapshots/maps-search` sits on the `publicCostly` rate bucket behind a 30s prepared-response cache (`searchResponses` in `maps-response-cache.ts`).

In compiled production with a local database, search cache misses run on the existing maps snapshot worker thread: counting, filtering, sorting, JSON serialization and compression all stay off the HTTP/SSE event loop. Requests share the prepared-response cache and its in-flight deduplication, with a bounded thread backlog. A worker failure or cooldown returns an uncached 503 with `Retry-After`, never a synchronous retry on the serving connection. Source-mode development, remote databases and the explicit `MAPS_SNAPSHOT_THREAD=0` switch retain the inline path.

## Map collections

Two things share the `/maps` Collections tab, switched by `cSrc` in the route's search params.

The auto packs (`features/map-collections.ts`, `map_collections` + `map_collection_members`) are code-defined recipes materialized from `map_search_index`: pattern x keymode x difficulty bucket on two axes (dan estimate and MSD overall), resampled from a quality pool on every rebuild so a pack rotates instead of pinning the same top 40. Read over `/api/snapshots/map-collection{s,}`, rebuilt by `rebuild_map_collections`, forced from the admin's "Rebuild now" on the grid.

The community half (`features/user-map-collections.ts`, `user_map_collections` + `user_map_collection_items` + `user_map_collection_favourites`) is collections players build themselves: a title, a description, up to five tags, and up to 100 charts in the order the author put them in, capped at 25 collections per account. A posted collection is public immediately and has no review state, because it holds nothing but beatmap ids and every one of those already passed osu!'s own moderation before it could reach the catalog it was picked from; the owner edits or deletes theirs and an admin can do the same to anyone's (`asAdmin` on update/delete), which is the only takedown path.

Membership is validated against `map_search_index` on every write, so an id the catalog does not know never lands in a list, and the three fields the cards show are derived from the members rather than typed by the author: the keymode chip (null, meaning mixed, unless every member shares one), the member count, and the three cover sets behind the collage (only sets with real artwork, same `?0` test the auto packs use). An edit that never opened the map picker omits `beatmapIds` entirely, which leaves the list and everything derived from it untouched.

A posted collection has its own page at `/collections/<slug>` (`src/routes/collections_.$id.tsx`), not a search param on `/maps`: this is the link players hand each other, and it loads on the server so a scraper gets the real title, blurb and card. The slug is derived from the title at creation and then frozen, so a rename never 404s a shared link, and `GET /api/map-collections/get` resolves either half (`where id = ? or slug = ?`). Ids are 10 hex characters rather than uuids for the same reason. The card is `/api/og?kind=collection&id=<id>` (`renderCollectionOg` in `src/routes/api/og.ts`), which draws the collection's own cover collage behind its title, owner and counts; it is R2-cached per id per OG version, so an edited collection keeps its old card until the version bumps.

Likes live in `user_map_collection_favourites` (one row per account per collection) with the count denormalized onto the collection row and recomputed from that table inside the same batch as the write, so a double click cannot drift it. Every route sits under `/api/map-collections/*` on the bridge, reads included: the directory is public, but who is asking decides which hearts come back filled and which rows a write may touch, so the viewer id is forwarded from the signed login cookie by the frontend server functions in `src/lib/user-map-collections.ts` instead of being taken from the browser. Neither table is pruned by retention.

## Farm helper

Recommends maps by comparing the subject player's top 200 against a global peer pool at similar PP, using candidates from `country_maps_farmed_scores` across all countries. Per-keymode (4k/7k) weighted PP lives in `farm_helper_user_key_stats`, seeded on first access.

Serving connections register a dedicated Farm Helper worker (`features/farm-helper-thread.ts` / `farm-helper-thread-worker.ts`), including in source-mode development. Snapshot misses send prepared subject state to one serialized worker, which selects peers, reads and aggregates farm rows, scores/ranks recommendations, and hydrates their top-peer previews using a query-only SQLite connection (32 MiB cache, mmap disabled). Only finished recommendations, stage timings, and small self-heal target lists return.

Profile resolution, feedback reconciliation, job enqueueing, and push-target reconciliation stay in the caller; first-use key-stat seeding and calibration persistence send their derived writes back through the caller's write connection. Snapshot caching, owner/public separation, coalescing, and invalidation generations remain on the serving connection; wholesale cache clears also invalidate the worker's peer pools before its next build.

Admission is capped at eight builds including the active one. A build has a 60-second watchdog; a crash/spawn failure/timeout rejects outstanding work and imposes a 30-second respawn cooldown. HTTP returns an uncached, retryable 503 with `Retry-After: 30` on worker failures or overload, without rerunning the build on the serving thread. Unregistered offline callers retain inline computation. Admin status exposes `farmHelperThread`; `Server-Timing` includes `fh_thread` and `fh_thread_queue` alongside the worker's original stage timings. Farmers and neighbors endpoints retain their existing separate paths.

The public snapshot, farmers, and neighbors routes hydrate only subjects already represented by a roster row or `profile_snapshots`; an arbitrary username returns 404 without touching osu!. The bridge-proven signed-in viewer is the sole cold-mint exception and is forced to their own numeric user id. This keeps Farm Helper from consuming the shared API budget as a username oracle.

`country_maps_farmed_scores` carries write-time lane columns (`key_count`, `speed_bucket`, `mods_key`; -1/null = unknown, readers fall back) so the peer aggregation filters by keymode in SQL and never re-derives mods per row; the whole cohort read stays inside the covering index `idx_country_maps_farmed_scores_user_lane`. A one-time boot backfill (`farmed_scores_lane_backfill:v1` in `live_meta`) populated existing rows. The A8 accuracy benchmark scale floors at 0.5, and gain-view snapshots report `belowGainFloorCount` (lanes dropped only by the 1pp minimum-gain floor) so `/farm-helper` can explain an empty (or thin) board and point at the popular view. The improve margin is relative above its floor (`max(8pp, 2%)` of the subject's score), so a high-pp play peers only nominally beat stops resurfacing as "improve". Gain snapshots also carry `practiceRecs` ("next tier"): lanes the hard feasibility gate dropped that the cohort farms and the subject never played, nearest MSD overshoot first, quoting the RAW peer median rather than a personal target; sparse keymodes contribute nothing (their gate verdicts are transferred-rating guesses, which is what kept a 7K main's barely-played 4K side out of the list) and the median must clear the 1pp gain floor. The frontend shows them under a thin unfiltered board.

Skillboost push targets are capped by the personal accuracy model when it has a prediction for the chart (accP85, the chart-specific ceiling the keymode-best accuracy cap cannot provide; a score already at/above it never pushes), and rows carry `subjectAccuracy`/`subjectMissCount`/`pushTargetAccuracy` so the UI can say "cut N misses" or "raise your 320-weighted acc from X to Y" instead of "cleaner acc". Feedback verdicts are `too_hard` / `too_easy` / `maxed`; `maxed` is a snooze (hides the lane from gain views under its own `maxedHiddenCount`, casts no feasibility-margin vote, expires after 60 days or on a new score). Skillboost (the "push" reason, self-improvement acc targets on owned lanes) is earned into the default view: every served gain board records its push lanes into `farm_helper_push_targets` (frozen at first suggestion), each build sweeps the stored rows against the subject's current scores, and reaching a suggested target - or covering most of the pp gap toward it - stamps the row achieved. Gain snapshots carry `pushUnlocked`; while false the frontend keeps skillboost rows (and their share of the headline total, excluded server-side) behind the skillboost tab. The table is never pruned by retention.

## Activity

Per-day player skill vectors (stream, jack, bracket, LN variants and friends) in `player_activity_*` tables, computed by `analyze_activity_beatmap` jobs. The analysis is versioned (`ACTIVITY_SKILL_ANALYSIS_VERSION`) for cache invalidation.

Activity reads serve existing projections immediately and queue `backfill_player_activity` to repair retained legacy gaps. The worker skips already projected scores, processes at most 2,000 retained IDs per batch and rebuilds the batch's day sessions before advancing its durable cursor, including on retries after interruption. Repair writes require the retained source score and an unsuppressed user in the same SQL statement so a concurrent wipe cannot recreate the player's activity. A `refreshPending` snapshot covers missing references and pending repair jobs; the open calendar refreshes with bounded backoff while visible, preserving the calendar through transient request failures. Opting out keeps old history; wiping a player removes their retained scores and repair jobs.

## Dan estimates

Sub-MSD-floor passes are retained separately in `plays_json.danOnly` (player skills v29). They carry judgement-based Dan evidence and no SSR values, pass the same chart/mod/vibro gates, and remain available after raw-score retention. The Dan calculation, evidence explorer and Dan sweep include them; MSD ratings, MSD play lists and accuracy-model fitting do not. Dan rules decide whether each earns credit or appears as “not counted”, independently of the Wife/MSD goal floor. A better rated attempt replaces the same chart/rate slot. The map popup distinguishes an unavailable MSD rating from a vibro exclusion. The version refresh reuses prior SSRs and recovers available scores through the normal compute path.

`dan_estimates` caches ratings keyed by a cache version from `live-backend/src/dan/`. Small batches are computed inline at request time; larger requests queue `compute_dan_estimate`. Version bumps keep serving the newest previous ready estimate while its replacement is queued, including custom-rate and Invert credit in player evidence and summary recomputes. Workers still require the current version, and previous results remain eligible for refresh. A completed current-version negative result supersedes old credit; malformed or mismatched-star-rating rows never become fallbacks. Score badges display the previous estimate alongside bounded background retries, retaining it if retries run out. Chart analysis refreshes likewise keep ready payloads readable through computation and transient failures. Since cache version 7 the estimates come from the unified chart classifier (`live-backend/src/dan/chart-classifier.ts`, routing 4K RC to LeoBlack Mixed, 4K LN to LeoBlack's LN interval table with the in-house kNN covering only what sits below that table's LN 5 floor, 6K/7K through Sunny interval tables), so 6K and 7K charts are supported.

Missing historical evidence is recoverable from any player's profile: **Add a missing score** on the Skills tab accepts an osu! score link, verifies that it is a passed mania score owned by that player, and sends it through the ordinary `ScoreIngestor` and dan gates. This is historical ingest, so it corrects stored projections and queues the player's skill recompute without fabricating a current tracker, snipe, top-play, session, or goal event. Anyone may submit the link because osu! supplies the ownership proof; scores the site already holds answer without another osu! API call. The paste bar clears immediately and queues links in the browser, processing one submission at a time while showing per-link progress and retryable failures. Pending duplicate links are ignored, and a failed submission does not block later links. Queued work continues if the dialog closes while the page stays loaded; it does not survive a page reload.

The same dialog carries an admin-only **Import a leaderboard** panel (`live-backend/src/features/leaderboard-import.ts`; `POST /api/admin/leaderboard-imports` behind the admin token, reached through the `importBeatmapLeaderboards` server function which checks the session first). It searches the site's own map index (the same `maps-search` snapshot `/maps` uses, so the same token syntax: `key=6`, `stars>5`, `creator=`, debounced as typed) narrowed to ranked or loved and sorted by plays, stars or ranked date in either direction, and imports one chart's global leaderboard, or every mania chart of a set. osu! publishes a map's top 50 and nothing past it, so that is the whole board. The route takes one id or a whole set's list in a single request (the dialog's **Add all** is one server-function call, so it no longer spends the frontend's per-visitor `serverFn` bucket per chart; an admin session is also exempt from that bucket once it would refuse, see `src/start.ts`), and enqueues an `import_beatmap_leaderboard` job per eligible chart (dedupe `leaderboard-import:<beatmapId>`, a queue reserve of 3 so a burst is never shed, the rest parked as `deferred_pressure` and reported as queued). A successful run writes `leaderboard_import_history`; both the route and the search-result controls enforce a seven-day per-chart cooldown from that durable receipt, so repeat clicks neither enqueue nor spend osu! API calls even after the two-day job row has been pruned. During rollout, retained `leaderboard_import` score events, successful top-50 entries in the seven-day API call log, and successful done jobs supply the same timestamp for boards imported before the history table existed. The dialog preloads `GET /api/admin/leaderboard-imports?ids=` for visible charts, marks when each board was imported, disables recent ones, and polls queued jobs for their state plus retained/durable stored count. After seven days `replaceDone` permits a refresh. Each score takes the manual-submission path (same suppressed live surfaces, source `leaderboard_import`, its own write turn), scores the site already holds are skipped by score identity, and the ingest's country gate is untouched: a board player from an untracked country is counted, not stored. A chart osu! refuses (not mania, no leaderboard) fails once with the reason on the job row and is parked, not retried. Both sources are excluded from the SSE ingest-freshness readout.

The table is keyed by `(beatmap, rate_percent)`, and the player dan clear rules read it for every rate the chart-analysis DT/HT columns do not cover: a play at any rate in the 0.5x-2.0x band (a lazer `speed_change`, or 1.5x/0.75x on a chart the boot sweeps never reached - the DT sweep only covered DT-farmed charts, which loved maps by definition are not) credits the stored verdict at its own `rate_percent`. Missing verdicts fill on demand: the skill compute computes a bounded batch inline in the same pass (`MAX_RATE_VERDICT_COMPUTES` in `player-skills.ts`, so the dan block it writes already credits them), and the dan-evidence read enqueues `compute_dan_estimate` for what its stored plays still lack. Plays set under lazer's Invert mod on 7K are rated against the inverted chart instead of being turned away (`live-backend/src/dan/invert-mod.ts` rebuilds it the way `ManiaModInvert` does: every object start in a column becomes a hold reaching a quarter beat short of the next object start, hold ends are ignored, the last object per column is dropped, breaks are cleared); the verdict for that chart lives in `dan_mod_estimates`, the same columns keyed once more by `mod_variant`, computed on demand at every rate including 1.0x, and never read as the chart's own. Such a play is a slot of its own (`StoredPlaySsr.inverse`), carries the `ln` and `lninverse` tags rather than the stored chart's, and so files under the 7K LN Inverse and General tiles. Hold Off and No Release still refuse a rating (`scoreRewritesChart`), as does Invert on every other keymode: 4K LN verdicts come from LeoBlack, which has not been checked against inverted charts.

What a clear credits moves with its accuracy (`live-backend/src/dan/dan-credit.ts`): the ladder's bar is the zero point (a bare pass credits the chart's full rawDan), accuracy above it credits a bonus on normalized headroom (+0.35 at half the headroom, +1.5 at 100%; the span is never narrower than `DAN_CREDIT_BONUS_MIN_SPAN`, the 4 points the decay window ran when the bonus was tuned, so widening the window never re-scales the bonus), and a pass down to 5 accuracy points under the bar credits a decayed level (continuous through the final point below a rice bar: at a 96% bar, 95% keeps -0.5075, 95.5% credits -0.25375, and 96% credits zero; reaching -1.25 four points under and continuing at that slope to -1.5 at the window's edge; the window was 4 points until 2026-08-31, and the knee at that mark is why widening it re-priced nothing; the 4K LN cap is 0.3). The rice near-bar taper shipped on 2026-09-06: it removes the immediate -0.26 cliff and changes only the last accuracy point below the bar, preserving every credit below that interval and at/above the bar. Reduced numerical credit may keep the chart's display tier; it is still below the full-clear requirement. The v28 player-dan sweep refolds stored evidence without rerunning MinaCalc. LN and course curves are unchanged. 6K/7K LN keeps that bonus but narrows its decay window to 3 points (1 until 2026-08-31, which cut off at 94% against the 95% bar and turned away runs worth a level or so down) and runs its own decay with a knee at a third of the window, so the first point under the bar prices exactly as the one-point window did (-0.26 at the bar to -1.25 at 94%, no existing clear re-priced) and the two new points extend a quarter level each, -1.5 at 93% and -1.75 at 92%, and 4K LN carries anchor tables of its own (`danCreditOptionsFor`, 2026-08-29): its bar is written in ScoreV2, where a 100% is out of reach on most charts with long notes, so scoring against a 100% top anchor paid +0.001 for a 98%. Its bonus is keyed in absolute points over the bar and tops out at 99.7% (97-98% -> +0, 98.5% -> +0.15, 99% -> +0.3, 99.5% -> +0.5, 99.7-100% -> +0.7, the same +0.7 top as before), and its decay runs from the 0.3 cap at the bar through -0.9 at 96.5% to -1.55 at 94.5%, 2.5 points under (a deeper bottom than the other ladders' -1.25, since a scrape at the edge of a 2.5-point window sits much further off the bar than a rice scrape at the edge of four). The knee half a point under the bar is what keeps the step at the bar itself small: the cap was 0.75 until 2026-08-29, which cost a full level between 97% and 96.99%. Credits clamp to the ladder's floor/ceiling (`danTableFloorFor`/`danTableCeilingFor`), every credited clear counts toward the quorum, and the aggregation (best-first mean over 20 weighted slots per skillset, skillset mean as the headline) reads credited values throughout. 7K LN is the one side whose headline is not that mean: its General tile wears the bare `ln` tag too, so it holds the whole body of LN work, and the headline follows it (`DanSkillsetBucket.anchor`, `anchoredSkillsetDans`), pulled by half of the other tiles' mean distance from it with each distance capped at two levels, so Tech, Inverse and Release together move it by at most a level either way. The reason is chart supply, not skill: measured on 2026-09-01 (`scripts/dev/ln-anchor-impact.ts`), Release sits a median 3.75 levels under General among the players who have the tile, 80% of them two or more under, and the gap widens with level (-5.2 at General 12-15) because the scene makes almost no release charts near the top, so under a plain mean a player at zenith on General, Tech and Inverse with a 10 on Release printed azimuth. A tile the cap bit is flagged `headlineCapped` (its own number is untouched) and the evidence payload names the anchor as `anchorSkillset`, so the modal can say which tile the estimate follows. Every verdict also stores how full its averaging window is (`clearWindow`: `have` of `need` clears, and a side headline sums every published skillset's window, so one thin skill leaves the side short, plus `skills: { full, total }`, how many of them have their whole window - the sum alone cannot be drawn honestly, since a side missing one skill entirely still reads 75 of 80); `DanLevelBadge` draws a ring in the badge's corner for anything short of it, filled continuously by the clear sum but onto 85% of the circle (`RING_MAX_SWEEP`), so an incomplete estimate cannot close the ring the way a true-scale 75 of 80 would; the tooltip counts skills where there are skills to count, which is how the dan chips on a profile and `/my-stats` and the rows on the `/rankings` dan board say an estimate is still filling in without being opened. A headline a course clear set carries no window, since a pass is not an average. Stored verdicts predating the curve are rewritten by the dan sweep (`player_skill_dan_sweep_done:v*`); the initial v17 pass derives only 4K LN from stored plays and atomically swaps that side into each affected row, so the previous visible verdict remains available until its replacement is ready and no SSR/MinaCalc recompute runs.


Rate variants share influence inside each dan pool (`weightedDanClearWindow` in `features/player-skills.ts`, 2026-09-06): order by credited dan and give each chart family's clears weights `1, 0.9, 0.81, ...`. Each clear keeps its credited dan; the window walks deeper until weights sum to 20, clipping its final contribution, or divides by the available weight for a thin pool. The four-clear quorum, primary-tile quorum, stray exclusions and course floors stay in place. `clearWindow.have` now measures weighted evidence and can be fractional. Skillset evidence ships every contributor, including those beyond the first 20 plays, with `repeatWeight` and actual `averagingWeight`; a multi-skillset headline has no single per-play weight, so its All clears list leaves weights to the skillset lists.

`features/chart-families.ts` groups verified reuploads in `beatmap_chart_families`: rate edits, and copies with a few notes slipped in (v2, 2026-09-11, after one chart turned up reuploaded 25 times with 1 to 8 extra intro notes each). Hashes of note columns and hold types over the first and last 64 notes find candidates (`head_key`/`tail_key`, so padding one end leaves the other key intact), then `sameChart` walks both note lists: every head and hold end must agree under a uniform time scale and offset with timestamp-rounding tolerance, and the longer chart may carry at most `paddingAllowance` extra notes (16, or 1% of the notes) anywhere. A changed, moved or removed note is a different chart. Two padded copies need not match each other, only the chart they pad, so a store that bridges families merges them. Titles, ids, difficulty names and declared rates do not establish a match. Fresh chart analyses register families; the cached-file-only `recompute_chart_family_sweep` backfills older charts without osu! API or MinaCalc work. The player-dan sweep waits for `chart_family_sweep_done:v2`, then refolds stored evidence. Unverified charts fall back to beatmap-id grouping, and Invert plays remain separate from the original structure. None of this changes a chart's classification.

Chart verdicts and player evidence are deliberately separate. The analyzer stores `classification_json.danEligibility`, derived only from the parsed note structure: eight or more objects sharing one column and head time is an exploit-sized stack and makes the chart ineligible for player dan clears at every rate, while `/maps` may still show the calculator's ordinary verdict for transparency. `dan_eligibility_recompute_done:v*` patches suspicious legacy rows from the cached `.osu` corpus, then the player-dan sweep removes their previously credited clears. This is identity-blind; no beatmap/title/mapper list participates.

4K handstream endurance takes precedence over the Speed near-tie when Stamina is the highest MSD skill and Handstream is second (excluding Overall), regardless of chart length. Handstream leading on its own does not earn this protection: community-confirmed speed charts such as Decoy, We Won't Be Alone and Vagrant have that shape with weaker Stamina. A chart whose standard-goal MSD has the Stamina/Handstream ordering and whose LeoBlack label is plain/non-trill also keeps the Stamina tile when a player's accuracy changes the SSR order. Jack demand, jack tags and the jack-share veto still take precedence, except that the veto spares a chart LeoBlack itself headlines as Handstream or as plain Jumpstream (no tech or trill in the label): the charts it wrongly caught were chordstream files whose chords also read as half-time chordjack clusters, and AiAe, its own case, stays on Jack through the jack-demand override. Re-derived by `player_skill_dan_sweep_done:v30`. This fixes The Fool's full chart and practice cut without chart-identity rules; `player_skill_dan_sweep_done:v27` refolds existing stored plays after deployment without rerunning MinaCalc.

Player version 27 refreshes previously computed rows to populate vibro explanations. Vibro exclusions retain their explanation separately in `plays_json.vibroExcluded` (`chart_vibro` for the base-chart gate, `rate_vibro` for the played-rate detector). These records never enter the rated `plays` pool, SSR reuse, or dan aggregation. They survive recomputes after the source score ages out and disappear when an eligible play replaces the same chart/rate slot. The Dan explorer includes them only when requesting rejected plays, showing “Vibro detected at 1.50×” or “Vibro detected in this chart”; map details also show the exclusion instead of presenting a numerical skill rating. Structural note-stack exclusions keep their separate `chart_ineligible` explanation.

### Dan course clears

`live-backend/src/features/dan-courses.ts` is a registry of the 87 real dan courses (Thaumiel's 4K Dan ~ REFORM ~, _underjoy's 4K LN v2 plus the two extra-level courses past 15, Jinjin's 7K regular and LN phases, Arkman's 6K regular and [Crz]sunnyxxy's 6K LN bands), canonical uploads only. A verified pass on one **floors** that (keymode, side) headline: `danSideFromClears` takes `max(averaged estimate, best course credit)`, and on a side with no quorum at all the course credit is the whole verdict. It never lowers a headline and never touches the per-skillset dans, which keep measuring the mix; the side records `courseClear` in `modes_json` when the course set the number, and the dan-evidence payload carries the best verified course pass (`courseClear`) when it set the number or sits on the headline's own level, so an Azimuth pass still shows under an azimuth+ average while a 5th dan pass under a 6th dan estimate does not. Nothing on the chart side changes: this is a player-layer rule, and the estimator stays identity-blind.

Each course names its level by its community label ("epsilon", "gamma", "terra"), resolved through the same ladder `danLabelFor` prints it back from (`danTableLevelForLabel` for 6K/7K, `danLevelForLabel` for 4K rice, the numeric ladder for 4K LN), and a registry test asserts the round-trip for every entry so a table change breaks the build instead of shifting every course by one. Accuracy is finer than pass/fail: the credit is the level plus an offset placed on `parseDan`'s own +/- thresholds relative to that ladder's bar (4K rice: 94% -> `delta--`, 95% -> `delta-`, 96% -> `delta`, 97.5% -> `delta+`, 98%+ -> `delta++`, capped under half a level so an overclear can never read as the next course - deliberately tighter than the chart-clear curve, because a course credit is a single-run floor with no quorum behind it, and the same play still earns the full chart-clear bonus as an ordinary rated clear). The scale is split at the bar: below it it stops at -0.26 rather than reaching 0, so a run that missed the pass mark can never print as a bare level, with a knee at one point under the bar so `--` is not squeezed into the first fraction of a point. The interpolation machinery is shared with the chart-clear curve (`dan-credit.ts`); only the anchor magnitudes are course-specific. On the live database the rule moved 395 sides across 360 players when it shipped (2026-08, before the accuracy credit curve; the averaged estimate outruns the capped course credit more often now, so the floor fires less). 4K LN credits from its bar up only, its labeler having no minus tier to render a sub-bar credit in. 7K LN courses use a deeper sub-bar curve (2026-09-04): just below 95% credits -0.26 levels, 94% credits -0.60, and 93% credits -0.75, with no course credit below 93%. This lets a run well short of the bar credit the preceding level: 93.14% stable on Gamma credits 10++ instead of forcing Gamma--. At-bar and overclear credit stay the same; the v25 player-dan sweep refreshes stored headlines from existing evidence.

Clears are read straight from `score_events` (the fresh window) and `player_activity_maps` joined to a passed `player_activity_score_refs` row (the 2-year archive), never from `plays_json`: that pool is deduped per (chart, rate), capped, and drops mod-blind archived rows, and on the live database only one of four players with a qualifying EXTRA-EPSILON pass still had it there. EZ/NF/HT/DC/RD, the key mods, the automation mods and any sub-1.0 `speed_change` disqualify a run; a row whose mods were never recorded is unverifiable and credits nothing. The bars are `danClearBarFor`'s, handed to the registry rather than duplicated in it. Rows written before this shipped are rewritten by the dan sweep (`player_skill_dan_sweep_done:v*`).

A backfill computed on one machine can seed another DB: `npm run export:chart-analysis` -> gzip/scp -> `npm run import:chart-analysis:dist -- <file>` (idempotent; missing rows land, newer full computations replace older rows only for immutable settled maps, and a full map search index rebuild is scheduled afterwards).

## Profiles and rankings

`player-profiles.ts` caches a best-200 snapshot for 24h (projected forward by top-play events) and profile sections (about, recent) for ~2 minutes. Initial profile fetches and both profile refresh jobs seed the About cache from the user payload (sanitized HTML plus raw BBCode), so opening About during that window reuses the existing osu! response; missing or expired sections still fetch on demand. Opening a profile serves the stored snapshot and queues its osu! work (`refresh_profile_user`, `refresh_profile_snapshot`); the only osu! call left on the request path is minting a player never stored at all, which is what a search for an untracked player does. **Load osu! recents** is display-only for an untracked player. For someone already in tracking scope, its fresh payload is also reused to fill gaps without changing their roster scope; the authenticated **Track my plays** action is the profile's explicit opt-in path. A valid dynamic-signature resolve is also a bounded demand signal for a tracked rank-null owner: at the roster refresh cadence it queues the existing full-snapshot job for Insights/Maniacard, or the one-call user job for an open PP/rank goal. Ranked members are skipped because their roster/top-play paths already maintain the same projections, and Skills/Dan need no extra profile call because tracked sessions recompute them directly.

Presence follows from that: the green dot means a tracked play inside the 10-minute session window and nothing else (osu!'s own `is_online` is ignored here since it also counts idling and browsing; the rankings list still shows it, from a live call, on purpose). Last seen is the newest of the last tracked play and the payload's `last_visit` while that payload is inside its refresh TTL; neither available means no last-seen line at all.

`keymode-pp.ts` backs the per-keymode pp totals the Key Split card opens on a profile. osu! publishes a cumulative figure for 4K and 7K and for no other keymode, and both are built from the top-200 window it serves, so a keymode played on the side reads far under the truth. `GET /api/profiles/{userId}/keymode-pp` answers with the pp plays this site tracked that the window cannot show: `player_activity_maps` reduced to one row per map (the ingest keeps it for years, so it holds plays that were never in the window; which row a map's group is quoted from is decided by `activityMapBestRowOrder`, best pp then latest day then rowid, and the detail prune and both sweeps order by the same thing so a tie cannot leave them disagreeing), joined to `maps_beatmaps.cs` with `map_search_index.key_count` as the fallback, capped at 200 per keymode. Both key-count sources are mania-only tables, so a convert has no row to join and drops out on its own, which is what osu! does with converts too; a map neither source knows is counted in `unknownKeyCount` and skipped, so every total stays a floor. The frontend merges it into the window in `calculateUserProfileInsights` (window play wins a map in both, list capped at 200 per keymode) and shows `trackedCount` in the modal. The `+` bound stays measured from the window alone: an unseen play is only known to be under the cutoff, so it could still outrank every tracked one. Measured on one profile: 4K +77pp (leaving 461 against osu!'s own figure, of which ~417 is the playcount bonus this deliberately omits), 7K +37, 6K +1,165 on 11 window plays. The Best Performance tab lists the tracked plays inline once a keymode filter is picked, ranked among the window's own rows and cut at the same 200 the modal's total is built from, ranked and cut before the mod filter so the two numbers describe one set of plays. A keymode filter also drops converts there, for the same reason the totals do: a convert on that list would be a row the total beside it never counted. They stay under "All", which is what osu! ranks, and the Recent tab keeps the plain filter since nothing there is a total; the Key Split modal only totals them, since the tab is where the list lives. Both wait for the whole window: the SSR loader seeds 50 of its 200 scores, and merging against those would label a play the window does hold as tracked and then drop the row.

A tracked row draws only from what the day-best row stored, and never asks osu! for anything: 200 rows on screen must not become 200 rate-limited calls, and a play that far back has usually been pruned at osu! anyway. Ingest records `best_max_combo`, `best_total_score`, `best_has_replay`, `best_solo_score_id` (the solo id `/replay` resolves, kept apart from `best_score_id`, which prefers a legacy id when one exists) and `best_played_at` (the instant of the play the row describes; `last_played_at` moves with every later attempt that day, so on 6% of rows it names a different play). The first four are kept for one play per map, the way an osu! profile keeps one: a map played on twenty days is twenty rows, the lists quote only one, so a better play clears them off every row it beat (`clearSupersededPlayDetails`, run only for plays worth pp, and deciding "beat" by the same row ordering the endpoint reads by so a tie leaves one copy rather than several). `best_played_at` is not pruned: it is that day's own fact and costs one timestamp. Mods and judgement counts deliberately stay on every row, because the dan pipeline reads each archived day-best on its own rather than only the strongest. None of this touches top-play detection: that runs off the osu! top-200 window in `top-plays.ts`, which never reads `player_activity_maps`, so a tracked tail play never announces itself as a new top play. `features/activity-play-details-backfill.ts` fills those for rows written before the columns existed, once, behind boot, from local payloads only: `score_events` while inside its 14-day retention, then `top_play_events`, `snipe_events`, and finally the two board tables for rows with `is_lazer = 1`, whose score id is then guaranteed to be the solo one. A candidate is matched by score id, in the id space the row itself recorded, so every source computes that same legacy-preferred id. The first two versions matched on (user, beatmap, pp to two decimals) instead, which is not an identity: 321 groups on the live database had two plays of one map rounding to the same pp, and a row could end up with another day's replay link. Score ids cost nothing here (every row with pp carries one, and id matching reached 245,028 of the 245,491 rows pp matching did) and cannot be ambiguous. Two heals run before the fill, since the pp-matched version already shipped: details come off any row that is not its map's best, and off any row a pp match could only have guessed at, which the fill then re-derives from the right score. What no local source holds stays null and reads as unknown: a row with no combo shows a dash, and a row with no id shows no replay button rather than a dead one. On the 11 GB local snapshot the v3 pass healed 51,684 rows and filled 195,035 of 554,667, leaving no map with more than one detail copy and no row whose stored solo id its own score contradicts; on one profile's 220 tracked maps that is a replay button on 200 and a combo on 75, and every play ingested from here on carries all three inline. Combo is the one field no local table keeps, so `features/activity-combo-backfill.ts` recovers the rest from osu! itself: a boot-seeded, self-chaining job (20 rows every 150s, ~8 calls/min in the limiter's job lane), sharing the archived-mods sweep's id-space handling and row verification, checkpointed in `live_meta` and reported on the admin page's sweeps panel. Its work list only holds rows a profile can actually draw, which is far fewer than the rows missing combo: one row per (player, map) rather than per day, nothing already inside the player's osu! top 200 (that renders from osu!'s own payload), and nothing whose keymode no mania table knows. Measured on the local snapshot that is 300,474 raw rows -> 217,298 -> 184,127 -> 177,284 over 4,892 players. Still 15 days at this chain's pace, so it is capped on top: `ACTIVITY_COMBO_BACKFILL_PLAYERS` (400) taken by pp, `ACTIVITY_COMBO_BACKFILL_ROWS_PER_PLAYER` (40) strongest-first within each, and `ACTIVITY_COMBO_BACKFILL_PIN_USERS` taken whole and sorted to the front. That is 9,341 rows, under a day. Everything past the cap is covered the cheap way instead: `features/activity-detail-on-demand.ts` watches the `keymode-pp` read, and when somebody actually opens a profile's per-keymode lists, any play on them still missing its details is queued for one osu! call after the response has gone out. So profiles that get looked at complete themselves and profiles nobody opens cost nothing. Both it and the blind sweep hand each filled row to `clearSupersededPlayDetails` afterwards, because a better play can land on that map between a work list choosing the row and the call returning, and the sweep's list additionally drops a row that has stopped being its map's best (the prune blanks such a row's combo, which would otherwise read as "still needs a call"). The sweep also waits for the local pass before building its list, since that pass fills rows for free that would otherwise eat its capped slots. It enqueues on the bookkeeping connection (never the serving one), skips a player whose chain is already in flight, skips rows the blind sweep has already queued, chains 20 rows a minute rather than bursting, and takes a worker lane of its own. It shared the sweep's lane at first, on the reasoning that one claim slot capped the two of them at one archived-detail job at a time, but a view-driven job is the higher priority of the two and profile views never stop arriving: on prod the sweep sat queued at 20 of 9,325 rows for two days behind 778 queued view jobs. So they are two lanes now, one claim each, and what caps their combined request rate is the shared limiter's job lane rather than the queue. Each link takes its own dedupe key (`:<userId>:<link>`), because the queue's conflict clause only updates a queued, failed or deferred row: a job enqueuing its continuation under the key it is running as writes nothing, which stopped the chain after one chunk and left a `done` row blocking the next profile view for two days. A score osu! cannot serve (pruned, or an id that resolves to somebody else's play) is recorded in `activity_play_detail_misses` and never asked about again. The archived-mods sweep writes the same columns now too, since it already holds the payload they come from, and hands the row to the same prune afterwards: its work list is ordered by dan rating, so the day it filled is not necessarily the one a profile lists. Clicking a tracked row opens the same details card a window row does, built on the spot by `lib/tracked-play-score.ts` from the row itself: no fetch, because 200 rows on screen must not become 200 rate-limited calls. The card is complete for any play whose judgement counts were stored (`best_statistics_json`, 91 of one profile's 220), and for the rest it drops the judgement grid rather than drawing six zeros, since an all-zero grid reads as a measurement of nothing. Stars and BPM come from the map at 1.0x and are left off a rate-modded play, which they do not describe. The osu! link and the replay button both use the solo id, which resolves for a stable play too.

`global-rankings.ts` serves a snapshot built from the union of every tracked country's roster (`country_rosters` joined with `users`, limited to tracked, ranked members with non-null pp), ordered by mania pp, with 7-day deltas from `rank-snapshots.ts`. A `pool=packs` query variant merges tracked rank-null members from both personal-tracking sources (`source in ('manual', 'score')`) into that board by pp, so opting in or being discovered from a score makes a player a pullable maniacard while keeping them off every leaderboard; pack-pool reads also skip the stat-repair enqueue. Adding `keys=4` or `keys=7` narrows the packs pool to players whose main keymode that is (higher variant pp from `users.pp_4k`/`pp_7k`, falling back to per-keymode farmed weighted pp from `farm_helper_user_key_stats`; players with no signal are in neither) - this backs the 4K/7K card packs, and a failed keymode build fails the request rather than serving the unfiltered pool.

`skill-leaderboards.ts` turns the stored per-player skill vectors and dan estimates into population boards ("the best 7K jack players"), served at `/api/snapshots/{skill-leaderboard,dan-leaderboard}` and rendered as the Skills and Dan tabs on `/rankings`. It adds no table and no job: one pass over every roster member's `player_skill_ratings.modes_json` builds an in-memory board cached per `Db` for 5 minutes (the pp board's shape, minus the `live_meta` pack), and scope/keymode/axis are read-time views of it, the way region rankings narrow the global board. Memory stays flat because a keymode holds one shared player record set plus, per axis, three typed arrays (value, evidence count, descending order of slots) rather than an entry object per player-axis pair. Skill boards cover every MSD-supported keymode from 4K through 18K and rank the **display-shrunk** rating (`shrinkMode` against the exact curves, imported from `skill-baseline.ts` rather than reimplemented) so a player's number on the board and on their own profile are the same number; ranking the raw aggregate would put a 22-play pool above a 215-play one. The two population floors in `skill-baseline.ts` are deliberately different: an axis publishes a shrink median from `BASELINE_MIN_USERS_PER_MEDIAN` members but a quantile curve (and therefore a percentile) only from `BASELINE_MIN_USERS_PER_CURVE`, because withholding the median is not neutral, it leaves one thin axis ranked raw next to neighbours ranked shrunk. `EXACT_SKILL_CURVES_FORMAT` versions that blob's shape so a change makes the weekly fold due once on deploy while the previous blob keeps serving. Keymodes with fewer plays than `BASELINE_MIN_PLAYS` are marked `provisional`, never hidden. The payload carries both the axes and keymodes that actually have a population in the requested scope, so neither picker offers an empty board and neither can drift from what a profile publishes (6K, 7K and 8K: pattern axes only; every other keymode: MSD skillsets plus `pattern:ln`, per `PATTERN_AXIS_KEY_COUNTS`), plus `shrunk` (per axis, not per board: false when THAT axis has no population median and is therefore ranked raw; dan snapshots carry no such flag) and `coverage` (rows at the current `PLAYER_SKILLS_VERSION`, so a half-migrated board after a version bump is visible rather than quietly wrong). Dan stays limited to its 4K, 6K and 7K ladders: those boards rank `rawDan` per keymode and side and are not shrunk, because a player dan is already an average of credited clears. They also carry a **skillset column** (`skillset=`, default `overall`): the per-bucket verdict the overall column averages, so 4K rice offers jack/tech/speed/stamina, 6K and 7K rice jack/tech/speed/stream, and 7K LN its four subtypes. The 4K buckets normally follow the play's strongest MinaCalc skillset, but a confident chart-analysis `speedjack` or `chordjack` tag overrides MinaCalc into Jack because its 4K model systematically reads speedjack as Jumpstream; the override moves the clear rather than duplicating it. What speed and tech mean on 4K is settled from the notes rather than from the ratings: `live-backend/src/dan/motion-features.ts` measures how much of a chart is wrist oscillation (two-column trills, minijacks, broken rhythm) against how much of it rolls across the hands, stores the shares in `classification_json.motion` (written by chart analysis, backfilled by `recompute_motion_features_sweep`), and a six-input logistic model (`SPEED_TECH_MODEL`) reads them alongside the MSD lead and the analyzer's tech score. Fitted on 738 charts from 170 mapper-named speed and tech packs with whole packs held out, it separates them at AUC 0.87 against 0.73 for the MSD lead alone, and the learning curve is flat from a quarter of the packs to all of them. Where it lands between its two bars (0.35 and 0.85 tech probability; the high bar was 0.75 until 2026-09-10, when a speed-tagged dump at 0.81 filed tech alone) the chart files under BOTH tiles, and the model only has a say while Stream sits within 1.75 MSD of the chart's best skillset (`SPEED_TECH_MODEL_MAX_STREAM_GAP`), since past that it is extrapolating off the near-ties it was fitted on and was putting jumptrill files on the speed tile; a stamina marathon whose base skillset is Stream or Technical and whose notes the model reads as tech files under stamina and tech (PEACE BREAKER [4K] FINAL PUNISHMENT, 777348, is the case that named that one). Primarily jack charts file under Jack only, regardless of duration or a Stamina/Handstream MSD argmax: jack endurance does not supply 4K stamina dan evidence. The v26 player-dan sweep removes that former shared credit from stored stamina verdicts and headlines. The remaining shared tiles are not a partition. A shared clear raises both tiles' dans but counts toward only the stronger tile's four-clear quorum, so it cannot open a skill on its own. A second, identity-blind override sits ahead of it: `live-backend/src/dan/jack-demand.ts` reads the chart's own note structure (`classification_json.jackDemand`, written by chart analysis and backfilled by `recompute_jack_demand_sweep`) and files a clear under Jack when the chart shows one of three shapes MinaCalc's anchored-row suppression hides: dense alternating chords that reload the same fingers two rows later, a chart LeoBlack reads as mostly jack clusters (the quadstream and minijack files, or a quarter jack clusters with the in-house chordjack detector and the raw jack pressure both corroborating), or a long jack marathon whose generic jack pressure stays high. It rates no chart and changes no dan; it only decides which player tile a clear is evidence for. Every arm only counts clusters slow enough to be jacked, because a repeat above roughly 230BPM has to be spread across fingers rather than re-tapped and that is the tech or speed demand, not the jack one. Measured as charts that change tile (not charts the verdict merely agrees with, since most jack-clustered files already win a JackSpeed or Chordjack argmax): 2.9% of a random 4K sample, 4.5% of the jack packs, 1 of 212 tech-pack charts, and none of the 399 speed, stream and handstream pack charts. Those per-bucket verdicts are stored in `modes_json` by `computeModeDan` rather than derived at read time (a roster-wide board cannot re-read every player's `plays_json`), off the same bucket walk the on-demand dan-evidence window uses, so "your jack dan" is one number wherever it appears. The payload publishes the columns that have a population, like `axes` does, and a row written before the verdicts shipped keeps its place on the every-clear column and is simply absent from the skillset ones until the dan sweep (`player_skill_dan_sweep_done:v*`, version-bumped whenever a dan derivation rule changes and every stored verdict goes stale; it re-derives from `plays_json` without re-rating, so the pass costs no MinaCalc) rewrites it from the plays it already has. A rebuild that throws keeps serving the previous board and pushes the next attempt out by a one-minute retry window rather than letting every request past the TTL start its own scan; a cold-start failure caches the error for the same window.

Dynamic signatures use `getCachedSignatureProfileSnapshot` for the projected best-200, player identity and artwork, omitting presence, keymode history and other full-profile fields. Insights and Maniacard versions hash these inputs rather than refresh timestamps or the last recorded score: below-window plays and unchanged refreshes reuse the finished image, while actual top plays, corrections, note BPMs and artwork changes move the version. The bridge resolve returns the same projected inputs used for that hash, avoiding another snapshot fetch; editor previews request `cached-snapshot?view=signature&lookup=id`. The note-BPM read excludes the broad status index from consideration so it looks up the requested beatmaps using the composite primary key instead of scanning every ready chart.

## Unrated plays

The board for the plays the skill ratings leave out, at `/rankings?tab=unrated`, and the matching Unrated plays view on the profile Skills tab. `unrated-plays.ts` owns both.

Its pool is exactly what the skill pipeline turns away, for two reasons. The plays in `plays_json.vibroExcluded` (`chart_vibro` for the base-chart gate, `rate_vibro` for the played-rate detector) never entered the rated pool. The plays on a chart the analyzer marked `classification_json.danEligibility.eligible: false` (the stacked same-column-heads structural gate, 26 charts in the corpus at the time of writing) stay rated for MSD but can never credit a dan; `[7K] FlexCORE!@#` (3343320) is the case that named that bucket. Sub-floor plays (`ratingExcluded`) are not listed: a play with no honest number on any axis is not what the board is for. Trimmed plays (`vibroAdjustment`) are not listed either, they are rated and appear under MSD plays.

Three numbers per play, none of which the ordinary pipeline reads. **pp** is computed locally: the chart's star rating at the played rate from the lazer port in `live-backend/src/dan/mania-star-rating.ts` (the Invert rewrite when the play used it), the play's own judgement counts, and the NF/EZ multipliers, through `live-backend/src/dan/mania-pp.ts`. Both modules moved under `dan/` from `src/lib/` so the replay viewer and the backend share one copy through the `#dan` alias; the frontend files re-export. A play whose counts are gone, or whose file rates a different keymode than the play (a key mod on a convert), gets osu!'s own pp when that is positive and nothing otherwise, rather than a guess. **MSD** is the Overall SSR with `adjustVibro: false`, every note counted, from `chart_raw_ssr`: chart-scoped on (chart, rate, Invert variant, score goal), which is everything the calc's output depends on, so one row serves every player who set the same play. A `chart_ineligible` play is not vibro, so its own stored vector already is the every-note rating. **Dan** is the chart's verdict at the played rate through `danClearTargetFor`, the same target the dan rules name when they reject the play, so the number on the board and the "aiming at" number in the dan list agree.

`unrated_plays` holds one row per (player, chart, rate, Invert variant) with those three numbers, the play's display fields and the stored play itself minus its vector, so the profile list needs no `plays_json` read. `refreshUnratedPlaysForUser` rewrites a player's rows from their latest stored pool: it runs after every `compute_player_skills` job (workers.ts, best-effort, after the ratings write, with a 12-run calc budget so a session's new vibro plays get their MSD now and the rest on the next compute) and from the boot-seeded `unrated_plays_sweep` (done-key `unrated_plays_sweep_done:v1`, 200 users a chunk in id order, prefiltered in SQL on `vibroExcluded` being non-empty or a pool play sitting on an ineligible chart, 40 calc runs a chunk, cached `.osu` only). A play the budget could not rate is stored with no MSD rather than left out, and the sweep holds its cursor while a page has deferred targets so it is never passed half-rated. Nothing here spends osu! API budget. `wipeUserProjections` clears the table.

The board is a read-time view over the table joined to `users`, cached per `Db` for five minutes, sorted in JS: the population is a few thousand rows, not the roster-wide scan `skill-leaderboards.ts` earns its typed arrays on. Scope, keymode, the All time / This week range and the sort are read-time filters. One row per player and chart, where a chart is its verified family from `beatmap_chart_families` (falling back to the beatmap id, Invert apart), so a player's reuploads of one chart hold one row (`chartKeyOf`), decided by the number being sorted on (`selectBoardRows`): the best pp play on a chart and its best MSD play are often different scores, a DT play usually wins MSD and loses pp, so each sort picks its own, and a row with no value on that axis is not ranked by it. The profile list keeps every rate of a chart (the explorer's rate cap handles repeats) and sends unpriced rows to the bottom rather than out. Endpoints `/api/snapshots/unrated-plays` (public, `keys`/`sort`/`range`/`page`) and `/api/profiles/:id/unrated-plays` (`keys`/`sort`, where `sort` is one of the three numbers or `recent`).

## Uploaded replays

A signed-in player can drop an `.osr` on `/replay`'s Upload tab; the file goes to R2 (`replay-cache/uploaded-replays/<id>.osr`, written by the frontend route `/api/replay-upload`, never lifecycle-expired) and everything human-readable about it is derived on demand into a gzipped description artifact (`replay-cache/uploaded-replay-desc/<id>.json.gz`). The backend owns only the owner index: `uploaded_replays` (id, `owner_user_id`, `owner_username`, `original_filename`, `uploaded_at`), which is what the `/replay/uploads` page ("Your uploads", linked from the Upload tab) lists and what authorizes a delete, since a share link is public and the `.osr` itself names no uploader. Routes `/api/uploaded-replays/{list,get,record,delete}` all take the admin-token bridge (the frontend forwards the osu!-verified viewer id; `asAdmin=1` + `all=1` is the admin's every-uploader view, which names the uploader on each row). The Upload tab's community list also names each upload's uploader, joined from this index (`uploadedBy` on `CommunityUploadEntry`, batched per page through `/api/uploaded-replays/rows`), because the card already names the player in the replay and those identities are not guaranteed to match. That list is the nine newest of the full gallery at `/replay/community` (`getCommunityUploadsPage` in `src/lib/uploaded-replay-community.ts`, 24 per page, newest first): both page over the same in-memory R2 listing of the `uploaded-replays/` prefix, rebuilt every two minutes or right away after an upload or delete on that instance, so the gallery shows every file that exists, indexed or not. Replay playback deliberately uses that uploader id to select the player's replay skin, even if an embedded score id resolves to somebody else: most uploads are the uploader's own plays, and an unindexed legacy upload simply falls back to the viewer's skin. A delete drops the row first and the R2 objects after, so a half-failure leaves an orphaned file `/admin/r2` can still see rather than a row whose share link still works. Rows are never pruned by retention. `backfillUploadedReplayOwners` (frontend server fn, admin-only, button on the admin view of `/replay/uploads`) rebuilds rows for uploads that predate the index from the `uploaderid` metadata stamped on each object. Uploads are unlisted, not private: the share link is public by design, so any new surface that offers to delete or list one has to go through `src/lib/uploaded-replays.ts` rather than the R2 key. Opening an upload takes the same path an ingested replay does: the server parses the `.osr` once into the packed frame shape (`packUploadedReplay` in `src/lib/uploaded-replay-open.ts`, artifact `replay-cache/parsed/uploads/v<n>/<id>.json.gz`, seeded by the upload POST) and resolves the chart in the same call (`resolveUploadedReplayBeatmap`: the checksum lookup, osu!'s `.osu`, and a contributed copy only when osu!'s is missing or is another revision), so `getUploadedReplayOpenData` is one round trip and the POST response itself carries the parsed replay and chart for the uploader's first view. The browser never downloads the raw `.osr` or loads the replay decoder for an upload; `/api/replay-upload?id=` remains only as the file download. Only production writes uploads to R2 (`uploadedReplaysUseR2()` in `src/lib/uploaded-replay-store.ts`): the local `.env` points at the same bucket, and the community list is an R2 listing, so a development upload would otherwise show up on the live site. Development saves and deletes on local disk (`data/replay-uploads/`, gitignored) and writes no description or packed artifact; reads still fall through to R2 so prod share links open locally, and the community lists merge the local drops with a read-only listing of the prod bucket so `/replay/community` looks populated locally. `REPLAY_UPLOADS_TO_R2=1` opts a dev server back into the R2 path.

When an uploaded replay's map can't be fetched from osu! (unsubmitted, deleted, or a locally edited revision, which is every case the analytics have recorded so far), the viewer asks whoever opened it for the `.osz`. The matched `.osu` goes to the community store (`replay-cache/community-beatmaps/<md5>.osu`, `src/lib/community-beatmap-store.ts`, content-addressed and never evicted) so the next viewer is not asked again. The song and background travel with it: after the `.osu` is accepted, the client posts the two files it pulled out of the archive to `/api/community-beatmap-asset` (multipart, same sign-in and rate limit as replay uploads), which stores them as `community-beatmaps/<md5>/audio` and `.../background`. A file is only accepted when the stored `.osu` names it (basename match against `AudioFilename` and the `[Events]` background line), its bytes sniff as an audio or image format, and it fits the cap (48 MB audio, 16 MB image); first write wins, so a later contributor cannot swap the song. `getCommunityBeatmapFile` reports which assets exist and the viewer then plays the audio through the same route (streamed from R2 with Range passthrough, so the `<audio>` element seeks and the stall-recovery fetch stays same-origin) and draws the background via a redirect to signed storage, exactly like `/api/background`. A bare `.osu` drop contributes nothing beyond the chart, which is why a community copy can still be silent. The Upload tab's community cards and `/replay/uploads` rows use the contributed background as the cover of a map that has no osu! cover (`communityBackground` on the entry).

## Skins

Skins carry a `visibility` (`public`/`private`) alongside `status`. A private skin is off `/skins`, off the duplicate guard, has no counted download or view, and 404s for anyone but its uploader (a true admin can still read it for moderation, and their private-skins shelf on `/skins` lists every uploader's, via `allPrivate=1` on `/api/skins/list`). Its R2 objects live under a `p-<secret>` key segment, never get a public bucket URL, and only answer to `?t=<secret>`, which `toSkinSummary(row, { asOwner })` attaches for owner-scoped reads only - so any new endpoint that serves a skin must go through that serializer rather than the row. Replay viewers never receive a private `.osk`: `/api/replay-skin/bundle` builds a zip of just the assets that player's stored settings draw (`live-backend/src/skins/replay-bundle.ts`, in-memory cache, no derived artifact in R2) and the client opens it exactly like an archive. What that protects is the file and the page, not the pixels a replay puts on screen.

A skin carries two dates, because the two stopped being the same once uploads could start out private. `published_at` is when the `.osk` was uploaded and the row published; `listed_at` is when the skin first became visible to everyone, stamped by `finishSkin` for a public upload and by `setSkinVisibility` the first time a private one is turned public (null until then). Every `/skins` sort orders and ties on `coalesce(listed_at, published_at)`, so a skin uploaded in January and made public in August opens the browse page instead of arriving seven months deep, where nobody would ever have scrolled to it; the browse cards and the skin page's relative time follow the same date, and the page's "Uploaded" fact row stays on `published_at`. Only the first listing stamps, so pulling a skin private and putting it back is not a way to bump it to the top of newest. Existing rows were backfilled once with `listed_at = published_at` for the public catalog.

The `/skins` trait filters read columns the server derives from each `.osk` at upload/replacement (`live-backend/src/skins/archive-meta.ts`, backfilled once at boot by `backfillSkinArchiveMeta`): `lane_cover` (a `lanecover`-named file, a stage hint whose drawn pixels run taller than 200px at 1x, or a `StageBottom` canvas whose screen-space opaque pixels cover a meaningful part of the top lanes - the two community cover tricks), `mania_stage` (the skin draws its own stage rails: per keymode block, `StageLeft`/`StageRight` resolve from the skin.ini reference with animated-frame and default-filename fallbacks, and the art must have visible pixels - the circle templates hide their stage with broken references and fully transparent blanks, and their leftover stage-named files don't count; `StageBottom` and `StageHint` are not stage-rail evidence), and `lazer` (lazer's editor files by basename - `skininfo.json`, `MainHUDComponents.json`, `SongSelect.json`, `Playfield.json` - or the metadata comment older lazer builds appended to skin.ini). "Stable" on the filter row means the complement of `lazer` and counts unanalyzed rows in, since lazer edits only add files and every upload is validated to carry stable `[Mania]` content anyway. `note_shape` (`circle`/`arrow`/`bar`/`other`) is classified per keymode from the visual signature's trimmed aspect and 8x8 alpha mask (`classifySkinNoteShape`): bars are wide, circles need circular shoulder/area geometry as well as symmetry, arrows have one-axis asymmetry, and a guarded multi-direction `skin.ini` arrow layout rescues arrows blurred by the compact mask only when the referenced sprite also has one-axis asymmetry at full resolution (circle art inherited under `arrows/left`, `up`, `down`, and `right` paths stays a circle). The skin-level label is the majority of its keymode labels, with a tie going to the lowest keymode. A shape-filtered list also returns `filterKeys`, selecting a stored preview whose own keymode has that shape: the starred render stays when it matches, otherwise a 4K cover searches around 7K (with 7K+1 treated as 7K) and vice versa, so the card visually proves why a mixed skin matched. The screenshots filter is just `screenshots_json` being non-empty. `resolution` is the one column no analysis writes: the uploader's optional "made for" answer, normalized to `WxH` by `normalizeSkinResolution` at upload and editable with the details; the filter matches it exactly. Its chips are not a fixed ladder but a facet: `listSkins` returns the distinct resolutions matching the rest of the query (its own predicate excluded, so a pick can be swapped or cleared), smallest display first, and the row is absent until an uploader answers. The `SKIN_RESOLUTION_PRESETS` list is only the datalist behind the upload and settings inputs.

Skin summaries additionally expose the distinct `noteShapes`, with the primary/majority authored shape first, so the detail page describes mixed skins (for example, "Bars, Circles"). When a declared keymode resolves neither its referenced tap sprites nor the stable default filenames, the visual signature records that keymode separately as a fallback bar: stable and the generated preview both draw a flat default there, so the skin appears under Bars without inventing mask/colour facts for similar-skins scoring or letting optional broken blocks outvote authored art. A Bars-filtered card can select one of those fallback keymodes as its proof preview just like a keymode with authored bar sprites. The scalar `note_shape` remains that primary label, while the shape filter searches the persisted `note_shapes_json` set so a mixed skin appears under every shape one of its keymodes actually uses.

Catalog preview rendering uses the same imported per-keymode layout as replay playback: receptors are anchored from `HitPosition` instead of the preview canvas edge, `KeysUnderNotes` controls whether they cover landing notes, the hit line keeps `ColourJudgementLine` (including deliberately invisible black), and judgement/combo art uses `ScorePosition`/`ComboPosition`. This keeps padded legacy key and lighting textures aligned even when the card raises the hit line for readability.
