# Frontend Reference

Deep reference for the frontend: route/component map, live data flow, client state, replay video export, OG images, the BBCode editor. The condensed guide is `AGENTS.md` at the repo root.

## Route and component map

- `src/routes/`: file-based routes. Shared shell, auth, country context, theme bootstrap, and live-backend bootstrap live in `src/routes/__root.tsx`. API routes in `src/routes/api/` (OG images, sitemap, audio/avatar/background proxies, replay upload, osu! OAuth, and `/api/sync`, the analytics capture proxy that writes to the live backend's in-house analytics store). A non-api server route `src/routes/videos/$id/$filename.ts` 302-redirects to a signed R2 URL for exported replay videos. Admin pages in `src/routes/admin/` (`live-backend`, `discord`, `dan-classifier`, `og-preview`, `r2`, `bbcode-images`, `todos`, `translation-reports`, `collections`, `dynamic-renders`, `ghost`). Files prefixed with `-` are tests, not routes. Do not hand-edit generated `src/routeTree.gen.ts`.
- `src/components/`: shared UI in feature folders (`layout/`, `home/`, `player/` incl. `maniacard3d/` and `bbcode/`, `replay/`, `maps/`, `rankings/`, `farm-helper/`, `packs/`, `me/` (goals + My Data panels), `ghost/`, `discord/`, `legal/`, `settings/`, `ui/`), plus a few loose top-level state-screen components (`BackendOfflineScreen.tsx`, `CountryWarming.tsx`, `LiveDataEmptyState.tsx`, `SnipesNotTracked.tsx`).
- `src/store.ts`: the Zustand client store. `src/lib/`: server/data utilities, the osu! API layer, replay modules, dan estimator.
- Utility scripts live in `scripts/` (dan benchmark/analyze, replay capture/validate, ghost atlas packing, plus `scripts/dev/replay-video-job.ts`, the Vite dev middleware fallback for replay video). Static assets live in `public/`.

`/rankings` hosts four boards behind one `PageTabs` bar: the pp ranking it has always served (`PpRankingsBoard`, still in `src/routes/rankings.tsx`) plus the skill, dan and unrated plays boards in `src/components/rankings/`. All four are public. The unrated plays board (`UnratedPlaysBoard`, `?tab=unrated`, params `sort` and `range` on top of `keys`) is the one whose rows are plays rather than players: a map and the player who set it, with the pp the site computes itself, the every-note MSD and the chart's dan, and the sort picks which of a player's plays on a chart shows (`src/lib/unrated-plays.ts` for the types; `docs/features.md` for the rule). It reads through the same client cache, and after each board lands it warms the other range and the other two sorts so those flips are cache swaps rather than skeletons; the keymode picker keeps the last board's keymode list across a fetch so the control row never re-lays out. Its row links the map to `/maps?map=` and the player to their profile, and its chart dan uses `DanMark` in `src/components/player/`, the play-row renderer the Skills tab's explorer also draws (no "~": it is the chart's verdict, not a player estimate). `head` indexes each tab's default board and marks every keymode/axis/side/page variation `noindex` with the canonical pointing back at that tab's default, since a variation is the same players re-sorted. Their params (`tab`, `keys`, `axis`, `side`, `skillset`, `sort`, `range`) share the route's `validateSearch` and its `stripSearchParams` defaults, and Nav's `/rankings` branch in `handleCountrySelect` preserves them so picking a country does not bounce the reader back to pp. The reads go browser-direct through `fetchLiveSkillLeaderboard`/`fetchLiveDanLeaderboard` in `src/lib/live-backend.ts`, with `src/lib/skill-leaderboard-cache.ts` (the farm-helper snapshot-cache shape, TTL matched to the backend board's 5-minute rebuild) making axis and tab flips instant on top of the endpoint's own `max-age`. The dan board's skillset row (`DanSkillsetPicker` in `LeaderboardControls.tsx`) is the axis picker's twin, driven by the populations the backend published and labelled from `DAN_SKILLSET_META`, the same pair the dan-evidence window draws; changing keymode or side drops back to every clear, since a bucket belongs to one ladder. `DanLevelBadge` in `src/components/player/` is the one renderer for a player dan level, shared by the profile's dan chips and the dan board. `/dan-estimates` (`src/routes/dan-estimates.tsx`) is the long-form article behind the dan board's caveat line: how a chart gets a dan, the per-ladder pass bars, the four-clear quorum and the skill breakdown. It is written in English only, like `/privacy` and `/terms`, and the corpus figures in it are dated in the text because they are measurements rather than live reads.

Replay-related logic is split across parser, validation, score input, skin, navigation, scroll speed, judgement, beatmap parsing, canvas rendering, and video export modules; keep changes scoped to the right module. Stable/lazer score differences matter; use existing score utilities rather than duplicating normalization.

The stable replay leaderboard is drawn in `ReplayCanvas.ts`; lazer uses its own retained Pixi cards in `LazerReplayLeaderboard.ts`, with the input types and ranking rules in `src/lib/replay-leaderboard.ts`. The two leaderboards save independent position, scale and reference geometry; stable stays within the stage, while lazer can extend past the left edge. Legacy shared placements seed both modes, preserving negative coordinates for lazer. Lazer replay rows stay expanded, as in the client when watching replays. They include avatars, accuracy and highest combo, reorder once per second, and scroll around the watched player. Avatar URLs go through the existing same-origin avatar proxy for canvas compatibility. Exports capture the same metadata, wait for these textures, and advance the lazer transitions using their frame timeline.

Fade-mask cleanup destroys the texture without destroying its source: Pixi's pooled alpha-mask filter retains that source until its next draw, and destroying it invalidates the filter for subsequent viewers and exports. Renderer teardown releases the GPU allocation.

## Replay video export

Export runs entirely on the user's device. No exported video is uploaded, no render job is queued, and the backend's `/api/replay-video-job` is not part of this path at all (`docs/backend.md` describes that dormant half). What still crosses the network is ordinary asset retrieval during preparation: the song, the background, the beatmap, the skin. Gated by `VITE_ENABLE_LOCAL_REPLAY_VIDEO_EXPORT=1`, plus admins while it is in limited release.

The whole thing lives in `src/lib/replay-export/`:

| Module | Responsibility |
| --- | --- |
| `timeline.ts` | Every frame index, sample index and event position, derived from integers. Nothing here reads a clock. |
| `render-spec.ts` | `ReplayExportSpecV1`: the serializable rendering intent, with runtime validation and a canonical form to hash. Holds no URL, handle, token or buffer. |
| `snapshot.ts` | `ReplayExportCapture` (taken synchronously from the viewer at the click) and `resolveReplayExportResources` (takes ownership of the bytes). |
| `manager.ts` | The app-level single-job owner: admission, Web Lock, subscriptions, unload guard, wake lock, cleanup, result lifetime. |
| `runners/local.ts` | One run, start to finish: plan, smoke encode, admit, render, mix, mux, commit. |
| `renderer.ts` / `composition.ts` | A job-owned renderer using the captured viewer viewport, uniformly fitted into the output canvas; backdrop pre-rendered once. |
| `audio/` | Range decode (`decode.ts`), sliding PCM window, resampler, WSOLA time stretcher, offline hitsound mixer, and `pipeline.ts` which joins them into one-second blocks. |
| `capabilities.ts` / `limits.ts` | Codec and destination probing; presets, admission caps and size estimates. |
| `destinations.ts` / `save-picker.ts` | Position-aware file writing with commit separated from muxer close, the bounded in-memory path, and the save dialog. |
| `encode.ts` / `quality-video-source.ts` / `video-quality.ts` | Mediabunny muxing and bounded native AV1 quality encoding: one video track, one audio track, interleaved. |
| `errors.ts` | Stable codes (`export_busy`, `unsupported_video_codec`, ...) and their copy. |

Things worth knowing before changing any of it:

- **The toolbar opens options.** The whole Export video button opens the range/preset panel; only its inner Export video action opens the save dialog or starts a download job. Custom range marks are set with Start here / End here inside that panel. Seeking the same replay keeps the panel open, including the separate phone/fullscreen seek bars; Escape and unrelated outside clicks still dismiss it. Opening the options lazily probes hardware video support at the selected dimensions and bitrate. Fast export is preferred when supported; otherwise Smaller file is automatically selected, Fast export is disabled, and the panel explains that encoding will use the CPU. Checking another preset rechecks support, while an explicit Smaller file preference remains selected even if hardware becomes available. Nothing starts until the user confirms Export video. Starting a job pauses the same live replay to avoid drawing both renderers at once; cancelling the picker does not pause playback.
- **The job outlives the route.** `ReplayExportPanel` is mounted in `__root.tsx`, not on `/replay`; the route only submits a capture and subscribes. Navigating, changing the skin, or opening another replay cannot touch a running job. Closing or refreshing the tab does end it, and that is stated in the dialog rather than worked around.
- **Ownership, not URLs.** The job fetches its own `Blob` for the song and its own `ImageBitmap` for the background, and copies the hitsound player's sample map. A `blob:` URL string the route can revoke is not ownership.
- **Export presets use exact 16:9 dimensions.** 720p30/60 means 1280×720, and 1080p30/60 means 1920×1080. The route captures `getOverlaySettingsSnapshot({ resolveLayout: true })` and the viewport. Export composes the same 16:9 fullscreen layout at the viewer's logical width, then scales it to the preset pixels. It does not add bars, crop the stage, or stretch notes. Live viewer preferences stay untouched; legacy wide specs remain supported. Viewer time/speed labels and performance diagnostics are omitted.
- **Fullscreen and export share overlay geometry.** Before resizing, the renderer resolves visible overlay bounds into their reference geometry once. An enabled leaderboard's bounds participate even while scores are loading or Tab hides it, so load order cannot leave it out of the hand-stats group. Side HUD sizes follow viewport width, so extra fullscreen height alone does not enlarge them. Side overlays sharing vertical space, plus the leaderboard/hand-stats group, retain their horizontal gaps as a group. Unused gutter space is discarded first, isolated overlays can shift, and groups shrink uniformly only if their occupied content cannot fit. Lazer's 768-coordinate leaderboard scale is resolved into the same model instead of bypassing it. The leaderboard retains its relative vertical center as it scales. Saved positions remain backward-compatible; unchanged preference refreshes do not re-author a resized layout, preventing fullscreen round-trip drift.
- **One clock.** `timeline.ts` is the only source of frame and sample positions. `modRate` is applied once, in the captured `effectiveRate`; the renderer gets it as `speedMultiplier` and must not have it applied again.
- **The hitsound schedule comes from the renderer** (`getHitsoundSchedule` on `ManiaReplayRenderer`), so sample precedence, layered-sample rules and combo-break logic are the viewer's, not a second implementation. The offline mixer places them at exact samples, keeps tails that began before the clip, and matches the viewer's 48-voice steal.
- **Pitch.** When the mods keep the pitch, `audio/time-stretch.ts` (WSOLA, in-house, deterministic) does it; when the pitch follows the rate, `audio/resample.ts` does. Setting a playback rate is not an alternative for the first case.
- **Audio buffers are released as they are consumed.** The time stretcher exposes its earliest still-needed source frame, so both decoded and resampled PCM windows discard old chunks while preserving overlap/search history. If streaming decode is unavailable, whole-song decoding requires a finite duration/channel count from compressed packet metadata and must fit its PCM plus encoded-input budget before `decodeAudioData` runs. The fallback retains its owned channel planes without copying the whole song again; it also checks the decoder's actual result.
- **Commit is not muxer close.** A `FileSystemWritableFileStream` replaces the user's file when it closes, so `destinations.ts` parks after the muxer finishes and waits for the manager to commit or abort. Cancelling leaves an existing file untouched.
- **Buffered output is checked through finalization.** In-memory MP4 can defer writes until the muxer finishes, so the destination checks the completed buffer in its finalize callback and again before creating the downloadable Blob. An oversized final file is rejected even if every render-loop size check passed.
- **Codec support is measured, not assumed.** Fast export tries hardware-preferred H.264, AV1, VP9 and VP8 in that order, and each candidate must pass a short encode/mux at the actual dimensions/FPS. A failed candidate advances to the next hardware candidate; if none works, `fast_export_unavailable` asks for a lower preset or Smaller file. Fast mode never deliberately falls back to software encoding. Hardware preference is a WebCodecs hint the browser can ignore, not proof of hardware use or a temperature guarantee. Smaller file (and legacy specs without `encodingMode`) retains software-preferred AV1 quantizer 96, then the previous H.264/WebM compatibility fallbacks. MP4 audio uses native AAC or the lazily loaded `@mediabunny/aac-encoder` (pinned to mediabunny); WebM uses Opus. Encoding mode and quantizer are part of the serializable spec. AV1 quantizer input queues are bounded to four frames, packet writes apply backpressure, and finalization flushes the encoder before closing its muxer track.
- **Encoder stays out of the shell bundle.** `manager.ts` imports the runner dynamically; mediabunny and its WASM must never become a static import of anything mounted in `__root.tsx`.
- **Size estimates are approximate.** Fast export uses nominal 16:9 VBR targets of 1.5/2.5 Mbps for 720p30/60 and 3/4 Mbps for 1080p30/60. Smaller file retains nominal budgets of 1/1.5 Mbps for 720p30/60 and 2/3 Mbps for 1080p30/60; AV1 maintains its quantizer and lets size vary with scene complexity. Both modes scale video budgets by actual picture area and add 128 kbps audio. The dialog and job share the same dimension and mode-aware bitrate helpers. The displayed estimate is duration × combined bitrate; the additional 25% headroom is used only for admission and memory budgeting. Destinations enforce actual byte limits independently.
- **Custom bitrate is optional.** The export panel offers a 0.5–20 Mbps slider and numeric input with a live file-size estimate. Invalid values disable export. The selected value is captured in bits per second and used by admission and the actual encoder. Recommended Smaller file mode retains AV1 quantizer 96; enabling Custom bitrate switches it to AV1 variable-bitrate encoding (with existing compatibility fallbacks), so the input is never merely an estimate. Unchecking restores the recommended mode/rate. Variable-bitrate file sizes remain approximate.
- Browser-only behaviour (WebGL, WebCodecs, the save dialog, playable output) is not covered by the unit tests and has to be checked in a real browser.

Basic settings are included in the shared shell so the drawer opens directly onto usable controls, with no loading skeleton. The large replay skin editor stays separate and preloads on settings intent/open; while a cold editor or its skin assets load, its button shows progress and the current screen stays usable. The player 3D card still loads at its tab boundary. Replay opening starts the shared renderer import and the selected font request alongside replay data; comparisons and map previews reuse the same renderer import. Replay fonts are loaded only by their consumers, and canvas initialization explicitly waits for its selected face with a bounded fallback. Missing map covers load only Comic Neue. Peak KPS uses a prefix table built for the replay/rate and binary lookup during playback or seeking, rather than rescanning the replay on each HUD refresh.

The Maniacard `(?)` dialog has **Card rank** and **Progression** tabs (`maniacard3d/RatingExplainerModal.tsx`). Progression loads public rating/tier history only when opened, keeps loaded pages across tab switches, and shows a compact trend over the latest seven loaded updates. Hovering, focusing or tapping a chart point reveals its date, rating, tier and change; arrow keys move between points. Session cards expand into map-cover rows and trait changes (`ManiacardHistory.tsx`); map estimates and their difference from the session total keep their explanations in focus/tap-accessible info tooltips. Map mods use the shared `ModBadge` renderer. The help button remains available at World Class and on honorary cards. The trait model lives once in `live-backend/src/shared/maniacard.ts`; `src/lib/maniacard.ts` re-exports it alongside frontend tier styles. Changes to that model must bump `MANIACARD_HISTORY_VERSION` in the history recorder so saved ratings retain their provenance.

The L/R miss counter has three saved styles: **Classic** (the default), **Hit circles**, and **Leaderboard**. Choose one from its stage right-click menu or its Style selector in Skin settings → Overlays; the settings preview follows the selection. The style lives on the `misses` placement, so owner skins and local video exports retain it. All three use 17px labels at base scale and shadowed white type. Every style keeps odd-keymode thumb assignment clickable and keeps a stable footprint, shrinking only the number for totals above three digits.

Replay playback follows the song's media clock through temporary buffering and seeking. A failed song releases that clock so replay visuals and hitsounds can continue; a successfully loaded replacement source can take over again after resync. Queued playback and buffering also show a subdued centered spinner after 250ms, independent of the controls' hover visibility and inside the fullscreen stage.

The opt-in **Mania Replay Master** replay overlay reproduces [the original visualization](https://github.com/Mania-Visualization-Project/Mania-Replay-Master): judgement-colored note outlines, inset raw press/release bars, and dotted LN input trails on a black scrolling panel. Enable it from Skin settings → Overlays or the stage's right-click Add overlay menu, then drag/resize it like the other overlays. Both menus offer independent overlay scroll speed (0.25×–3×, with 1× matching the original default) and a transparent-background toggle; both persist with the placement and apply to video exports. `src/lib/replay-master-overlay.ts` indexes the renderer's existing note judgements and raw input segments; it uses constant-time scrolling with the replay's mod rate so SVs do not distort hit offsets. Like the reference, it previews the annotated notes approaching the bottom edge. The shared Pixi renderer includes it in video exports; existing mobile portrait/HUD visibility rules apply. Attribution and the Apache-2.0 license are in the module and `public/licenses/mania-replay-master.txt`.

`AddScoreModal` sends pasted scores to the backend's durable import queue. It serializes only the short admission requests, then polls accepted job ids in batches for queued/running states and final score or refusal receipts. Closing the modal stops polling; accepted imports continue on the backend. Already-stored scores can return a receipt immediately.

## Live data flow

Prefer `src/lib/live-backend.ts` for live backend calls from client routes: typed snapshot fetchers, `openLiveEventSource()` for SSE, and the country feature-tier bootstrap. Home, Tracker, Top Plays, Snipes, and Maps hard-require the live backend (no `VITE_LIVE_BACKEND_URL` renders a `LiveBackendRequired` notice; the osu!-API fallback scans were deleted). Server functions remain only for data the backend does not project: user profiles/scores, rank histories, per-beatmap country scoreboards (replay browse), beatmap search/files, dan estimates, OG cards. When an SSE connection drops, the browser's `EventSource` reconnects and replays missed events via `Last-Event-ID` against `live_event_log`; there is no polling fallback (`/api/sync` is unrelated, it is the analytics capture proxy). The live stream is also shared across tabs (`src/lib/cross-tab-event-source.ts`): tabs elect a leader per stream URL via the Web Locks API, the leader holds the one real `EventSource` and relays events over a `BroadcastChannel`, and on leader death the lock passes to another tab, which resumes gap-free through the backend's `?lastEventId=` replay. A visible follower that hears no relay for 45s (a leader tab suspended by the browser keeps the lock but relays nothing) quietly opens its own direct connection and drops it when the relay resumes. The relay forwards the event names in `LIVE_EVENT_NAMES` (`src/lib/live-backend.ts`) - a new SSE event type must be added there or follower tabs will never see it.

Keep authenticated osu! API access on the server. Do not put osu! credentials or direct authenticated osu! calls in client components. `src/lib/osu.ts` is a facade over domain modules in `src/lib/osu/` (rankings, maps, replay, snipes, tracker, top-plays, pattern-analysis, dan, users, beatmaps; plus shared support modules).

## Client state

The optional osu! cursor (`src/components/layout/CustomCursor.tsx`) uses a generated PNG as the native CSS cursor so movement is independent of page rendering. Its canvas draws only the trail and C-key smoke, and stops when those effects expire. Keep that canvas synchronized: `desynchronized` caused an opaque black overlay on some Windows drivers. Native cursor images, including the pressed variant, stay within 128×128 pixels; extreme glow settings compress the outer glow to fit.

Client state uses Zustand in `src/store.ts`, persisted to localStorage under `mania-hub-cache-v5`; bump the version on breaking shape changes. Data is country-keyed with `fetchedAt` plus TTL checks from `src/lib/cache.ts`. Persistence holds immutable snapshots for 250ms and serializes only the latest one, skipping updates whose persisted fields have not changed. Feed trimming happens at serialization; the stored format and 60-score per-country limit stay the same. `pagehide` and hidden-document events flush synchronously, with quota eviction and retry handling. Critical preferences (theme, hidden users, avatar accents) live in separate storage keys so they survive quota errors. Check `useHasHydrated()` before trusting persisted state during SSR hydration.

## OG images and SEO

Tracker, snipes and report pages serve `noindex` in their route heads and remain crawlable so search engines can read that directive. `/packs?view=streak` also serves `noindex`; the main `/packs` landing page stays indexable. The backend's streamed `.osk` downloads carry `X-Robots-Tag: noindex`, while public skin previews remain indexable.

The unfiltered newest `/skins` catalogue server-renders every page, with router links for pagination and a canonical URL for each page (`/skins`, `/skins?page=1`, and so on; page numbers are zero-based). Pages past the catalogue's end return 404 when the backend answers. Filtered, sorted and viewer-specific listings remain client-fetched and serve `noindex`. The anonymous SSR fetch retains its short timeout and seeds the browser cache without an extra hydration fetch; the sitemap continues to list every public skin detail page.

OG images are rendered by `src/routes/api/og.ts` (@vercel/og) and cached in R2 keyed by the `OG_IMAGE_VERSION` constant in `src/lib/seo.ts`; bump it there when changing OG layouts. Meta and OG URL builders also live in `src/lib/seo.ts`; the sitemap is `src/routes/sitemap[.]xml.ts`. Shared uploaded replays use their public upload id to render the normal replay result card from the persisted uploaded-replay description, since a manually uploaded `.osr` has no guaranteed public score id.

The frontend-wide API/server-function/OG limiter trusts `cf-connecting-ip` only when `TRUST_PROXY_HEADERS` is explicitly enabled. That switch is valid only for a Cloudflare-only origin; otherwise it stays off and all requests use the conservative shared `unknown` bucket. OG rasterization is single-flight per key and guarded by a hard two-render semaphore, including the cold default-card fallback.

Dynamic profile embeds (`/api/signature/$token/$variant`) keep five-minute freshness and allow a day of background revalidation, so a quiet profile can show its previous image while the edge refreshes it. The origin retains finished bytes within a 16 MiB bound; after 30 seconds it must revalidate the token, published type and ETag before reusing them. Token resolution and storage/render work collapse concurrent identical requests. Disabling, rotating, unpublishing and moderation purge the stable URLs, including legacy numbered variants; invalidation also prevents an in-flight request from repopulating local caches. Render failures return uncached 503s so the edge can use `stale-if-error`.

Signature fonts and Insights assets load in parallel outside the shared rasterization gate. The gate covers rasterization and WebP encoding; the editor preview uses the same pipeline. Versioned osu! assets have a bounded source cache, while custom image URLs keep their five-minute lifetime and the same pinned transport. `Server-Timing` reports the origin cache path and resolve, storage, asset, queue, raster and encode durations; when an edge serves a cached response, these are the timings of the origin fill, not the current browser request.

## BBCode editor

The BBCode editor (`/bbcode`, `src/components/player/bbcode/`) lays its visual and preview panes out at osu!'s real "me!" geometry rather than at whatever width the pane happens to be: a fixed 890px column at 14px, measured off a live profile page and constant from 700px to 2560px of viewport, in `src/lib/bbcode-layout.ts`. The column is scaled as one piece to fit a narrow pane (CSS `zoom` on `.bbcode-editor-frame > .bbcode-content`, never above 1:1), so `max-width: 100%` clips images exactly where osu! clips them. Images therefore sit at their file's own pixel width, which is what osu! does - it emits `style="width:<intrinsic>px"` per `[img]` and caps at the column, with no height cap. Nothing but the About card on a player page may cap a BBCode image's height (`.bbcode-content--capped`); doing it in the shared rule is what used to make the editor lie about size. Since `[img]` takes no width parameter, resizing means re-encoding the file: the drag handle re-cuts from the original bytes kept in `resizeOriginsRef` (so an image can be dragged back up, and repeated nudges cost no quality) and clamps to the profile column. Shrinks may use transparent padding to preserve source pixels; growth is written directly at the requested intrinsic width, even when that means upscaling. The preview stays pinned until the on-screen image element itself decodes the new file, so releasing the pointer cannot expose the old intrinsic width for a frame or permanently. Image re-encodes are serialized so two quick drags cannot race and let an older result land last. Ctrl/Cmd-click builds an ordered image selection; "Match sizes to first selected image" re-cuts every later selection to the first image's visible width. Resizing an already-hosted image reads it back through `GET /api/catbox-upload?url=` because a canvas cannot read cross-origin pixels without tainting; that is a download, and nothing is uploaded until Copy BBCode (the status says "Resizing", not "Uploading"). `performPinnedRequest` must send a `User-Agent` - catbox resets the socket without one, which made every catbox-hosted profile image fail to resize with a 503. `ImageEditorModal` (the "Resize / crop" dialog) is the same re-encode with a crop and an orientation on top; its "Resize to" fields are the resize, since the crop box only chooses which pixels survive. It keeps its own undo stack and swallows Ctrl+Z/Ctrl+Y in the capture phase whether or not it has a step to undo, because the editor behind it undoes document text on the browser's native stack and there is no way to put that back. Selected text in the visual surface is washed rather than inverted (`.bbcode-editor-surface ::selection`, background only): the colour and hue-shift controls act on a selection, so the OS highlight painting over it hid the very thing being adjusted. `[imagemap]` replaces an image rather than decorating one - it carries its own image URL and its areas, and osu! renders no `[img]` inside it - so in the visual pane the tool converts the image you picked (toolbar button or "Make imagemap" on its context menu) and seeds one draggable area; right-clicking a map adds or deletes an area, converts back to a plain `[img]`, or deletes it. In code mode the same button still inserts the raw template. Anything that reads staged images out of the document must go through `src/lib/bbcode-pending-images.ts`: a blob URL can now sit on an imagemap's first line as well as inside `[img]`, and missing one is a hard copy error rather than permission to silently omit the image. Copy reserves the clipboard during deferred uploads with a promise-backed `ClipboardItem`; once hosting succeeds the status changes from Uploading to Copying, and a stalled or rejected reservation gets one direct `writeText` fallback before the editor asks for an immediate retry.

Pending blob matching must accept bracketed IPv6 origins such as `blob:http://[::1]:3000/...`; Vite can serve local development on `::1`, and treating `[` as a BBCode boundary makes every newly pasted local image invisible to Copy BBCode.

## Footer version

The footer displays plain version text from `VITE_APP_VERSION`, baked into both SSR and browser bundles. Local and preview builds outside the VPS workflows default to `v2.176`. Both VPS workflows (`.github/workflows/deploy-web-prod.yml` for production and `.github/workflows/deploy-web.yml` for Ninja) read their own `$WEB_DIR/app-version-counter` over SSH before building, build with the next number as `v2.N`, and persist that number atomically after deployment succeeds, including the restart and Caddy health check when enabled. An absent counter starts at 175 for production and 176 for Ninja, so Ninja's first versioned deployment advances beyond its old `v2.176` fallback. The channels increment independently; their version numbers do not identify matching commits. Manual uploads with restart disabled also advance the counter because they ship a versioned bundle. A failure before the recording step leaves the counter unchanged. Each channel's concurrency group serializes its deployments. No repository URL or commit metadata is displayed. The major version prefix is a deliberate product decision; change it in both workflows and the footer fallback for the next major release.
