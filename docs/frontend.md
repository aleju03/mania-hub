# Frontend Reference

Deep reference for the frontend: route/component map, live data flow, client state, OG images, the BBCode editor. The condensed guides are `AGENTS.md` / `CLAUDE.md` at the repo root.

## Route and component map

- `src/routes/`: file-based routes. Shared shell, auth, country context, theme bootstrap, and live-backend bootstrap live in `src/routes/__root.tsx`. API routes in `src/routes/api/` (OG images, sitemap, audio/avatar/background proxies, replay upload, osu! OAuth, and `/api/sync`, the analytics capture proxy that writes to the live backend's in-house analytics store). A non-api server route `src/routes/videos/$id/$filename.ts` 302-redirects to a signed R2 URL for exported replay videos. Admin pages in `src/routes/admin/` (`live-backend`, `discord`, `dan-classifier`, `og-preview`, `r2`, `bbcode-images`, `todos`, `translation-reports`, `collections`, `dynamic-renders`, `ghost`). Files prefixed with `-` are tests, not routes. Do not hand-edit generated `src/routeTree.gen.ts`.
- `src/components/`: shared UI in feature folders (`layout/`, `home/`, `player/` incl. `maniacard3d/` and `bbcode/`, `replay/`, `maps/`, `rankings/`, `farm-helper/`, `packs/`, `me/` (goals + My Data panels), `ghost/`, `discord/`, `legal/`, `settings/`, `ui/`), plus a few loose top-level state-screen components (`BackendOfflineScreen.tsx`, `CountryWarming.tsx`, `LiveDataEmptyState.tsx`, `SnipesNotTracked.tsx`).
- `src/store.ts`: the Zustand client store. `src/lib/`: server/data utilities, the osu! API layer, replay modules, dan estimator.
- Utility scripts live in `scripts/` (dan benchmark/analyze, replay capture/validate, ghost atlas packing, plus `scripts/dev/replay-video-job.ts`, the Vite dev middleware fallback for replay video). Static assets live in `public/`.

`/rankings` hosts three boards behind one `PageTabs` bar: the pp ranking it has always served (`PpRankingsBoard`, still in `src/routes/rankings.tsx`) plus the skill and dan leaderboards in `src/components/rankings/`. All three are public. `head` indexes each tab's default board and marks every keymode/axis/side/page variation `noindex` with the canonical pointing back at that tab's default, since a variation is the same players re-sorted. Their params (`tab`, `keys`, `axis`, `side`, `skillset`) share the route's `validateSearch` and its `stripSearchParams` defaults, and Nav's `/rankings` branch in `handleCountrySelect` preserves them so picking a country does not bounce the reader back to pp. The reads go browser-direct through `fetchLiveSkillLeaderboard`/`fetchLiveDanLeaderboard` in `src/lib/live-backend.ts`, with `src/lib/skill-leaderboard-cache.ts` (the farm-helper snapshot-cache shape, TTL matched to the backend board's 5-minute rebuild) making axis and tab flips instant on top of the endpoint's own `max-age`. The dan board's skillset row (`DanSkillsetPicker` in `LeaderboardControls.tsx`) is the axis picker's twin, driven by the populations the backend published and labelled from `DAN_SKILLSET_META`, the same pair the dan-evidence window draws; changing keymode or side drops back to every clear, since a bucket belongs to one ladder. `DanLevelBadge` in `src/components/player/` is the one renderer for a player dan level, shared by the profile's dan chips and the dan board. `/dan-estimates` (`src/routes/dan-estimates.tsx`) is the long-form article behind the dan board's caveat line: how a chart gets a dan, the per-ladder pass bars, the four-clear quorum and the skill breakdown. It is written in English only, like `/privacy` and `/terms`, and the corpus figures in it are dated in the text because they are measurements rather than live reads.

Replay-related logic is split across parser, validation, score input, skin, navigation, scroll speed, judgement, beatmap parsing, canvas rendering, and video export modules; keep changes scoped to the right module. Stable/lazer score differences matter; use existing score utilities rather than duplicating normalization.

Basic settings are included in the shared shell so the drawer opens directly onto usable controls, with no loading skeleton. The large replay skin editor stays separate and preloads on settings intent/open; while a cold editor or its skin assets load, its button shows progress and the current screen stays usable. The player 3D card still loads at its tab boundary. Replay opening starts the shared renderer import and the selected font request alongside replay data; comparisons and map previews reuse the same renderer import. Replay fonts are loaded only by their consumers, and canvas initialization explicitly waits for its selected face with a bounded fallback. Missing map covers load only Comic Neue. Peak KPS uses a prefix table built for the replay/rate and binary lookup during playback or seeking, rather than rescanning the replay on each HUD refresh.

Replay playback follows the song's media clock through temporary buffering and seeking. A failed song releases that clock so replay visuals and hitsounds can continue; a successfully loaded replacement source can take over again after resync. Queued playback and buffering also show a subdued centered spinner after 250ms, independent of the controls' hover visibility and inside the fullscreen stage.

## Live data flow

Prefer `src/lib/live-backend.ts` for live backend calls from client routes: typed snapshot fetchers, `openLiveEventSource()` for SSE, and the country feature-tier bootstrap. Home, Tracker, Top Plays, Snipes, and Maps hard-require the live backend (no `VITE_LIVE_BACKEND_URL` renders a `LiveBackendRequired` notice; the osu!-API fallback scans were deleted). Server functions remain only for data the backend does not project: user profiles/scores, rank histories, per-beatmap country scoreboards (replay browse), beatmap search/files, dan estimates, OG cards. When an SSE connection drops, the browser's `EventSource` reconnects and replays missed events via `Last-Event-ID` against `live_event_log`; there is no polling fallback (`/api/sync` is unrelated, it is the analytics capture proxy). The live stream is also shared across tabs (`src/lib/cross-tab-event-source.ts`): tabs elect a leader per stream URL via the Web Locks API, the leader holds the one real `EventSource` and relays events over a `BroadcastChannel`, and on leader death the lock passes to another tab, which resumes gap-free through the backend's `?lastEventId=` replay. A visible follower that hears no relay for 45s (a leader tab suspended by the browser keeps the lock but relays nothing) quietly opens its own direct connection and drops it when the relay resumes. The relay forwards the event names in `LIVE_EVENT_NAMES` (`src/lib/live-backend.ts`) - a new SSE event type must be added there or follower tabs will never see it.

Keep authenticated osu! API access on the server. Do not put osu! credentials or direct authenticated osu! calls in client components. `src/lib/osu.ts` is a facade over domain modules in `src/lib/osu/` (rankings, maps, replay, snipes, tracker, top-plays, pattern-analysis, dan, users, beatmaps; plus shared support modules).

## Client state

Client state uses Zustand in `src/store.ts`, persisted to localStorage under `mania-hub-cache-v5`; bump the version on breaking shape changes. Data is country-keyed with `fetchedAt` plus TTL checks from `src/lib/cache.ts`. Persistence holds immutable snapshots for 250ms and serializes only the latest one, skipping updates whose persisted fields have not changed. Feed trimming happens at serialization; the stored format and 60-score per-country limit stay the same. `pagehide` and hidden-document events flush synchronously, with quota eviction and retry handling. Critical preferences (theme, hidden users, avatar accents) live in separate storage keys so they survive quota errors. Check `useHasHydrated()` before trusting persisted state during SSR hydration.

## OG images and SEO

OG images are rendered by `src/routes/api/og.ts` (@vercel/og) and cached in R2 keyed by the `OG_IMAGE_VERSION` constant in `src/lib/seo.ts`; bump it there when changing OG layouts. Meta and OG URL builders also live in `src/lib/seo.ts`; the sitemap is `src/routes/api/sitemap.ts`. Shared uploaded replays use their public upload id to render the normal replay result card from the persisted uploaded-replay description, since a manually uploaded `.osr` has no guaranteed public score id.

The frontend-wide API/server-function/OG limiter trusts `cf-connecting-ip` only when `TRUST_PROXY_HEADERS` is explicitly enabled. That switch is valid only for a Cloudflare-only origin; otherwise it stays off and all requests use the conservative shared `unknown` bucket. OG rasterization is single-flight per key and guarded by a hard two-render semaphore, including the cold default-card fallback.

Dynamic profile embeds (`/api/signature/$token/$variant`) keep five-minute freshness and allow a day of background revalidation, so a quiet profile can show its previous image while the edge refreshes it. The origin retains finished bytes within a 16 MiB bound; after 30 seconds it must revalidate the token, published type and ETag before reusing them. Token resolution and storage/render work collapse concurrent identical requests. Disabling, rotating, unpublishing and moderation purge the stable URLs, including legacy numbered variants; invalidation also prevents an in-flight request from repopulating local caches. Render failures return uncached 503s so the edge can use `stale-if-error`.

Signature fonts and Insights assets load in parallel outside the shared rasterization gate. The gate covers rasterization and WebP encoding; the editor preview uses the same pipeline. Versioned osu! assets have a bounded source cache, while custom image URLs keep their five-minute lifetime and the same pinned transport. `Server-Timing` reports the origin cache path and resolve, storage, asset, queue, raster and encode durations; when an edge serves a cached response, these are the timings of the origin fill, not the current browser request.

## BBCode editor

The BBCode editor (`/bbcode`, `src/components/player/bbcode/`) lays its visual and preview panes out at osu!'s real "me!" geometry rather than at whatever width the pane happens to be: a fixed 890px column at 14px, measured off a live profile page and constant from 700px to 2560px of viewport, in `src/lib/bbcode-layout.ts`. The column is scaled as one piece to fit a narrow pane (CSS `zoom` on `.bbcode-editor-frame > .bbcode-content`, never above 1:1), so `max-width: 100%` clips images exactly where osu! clips them. Images therefore sit at their file's own pixel width, which is what osu! does - it emits `style="width:<intrinsic>px"` per `[img]` and caps at the column, with no height cap. Nothing but the About card on a player page may cap a BBCode image's height (`.bbcode-content--capped`); doing it in the shared rule is what used to make the editor lie about size. Since `[img]` takes no width parameter, resizing means re-encoding the file: the drag handle re-cuts from the original bytes kept in `resizeOriginsRef` (so an image can be dragged back up, and repeated nudges cost no quality) and clamps to the profile column. Shrinks may use transparent padding to preserve source pixels; growth is written directly at the requested intrinsic width, even when that means upscaling. The preview stays pinned until the on-screen image element itself decodes the new file, so releasing the pointer cannot expose the old intrinsic width for a frame or permanently. Image re-encodes are serialized so two quick drags cannot race and let an older result land last. Ctrl/Cmd-click builds an ordered image selection; "Match sizes to first selected image" re-cuts every later selection to the first image's visible width. Resizing an already-hosted image reads it back through `GET /api/catbox-upload?url=` because a canvas cannot read cross-origin pixels without tainting; that is a download, and nothing is uploaded until Copy BBCode (the status says "Resizing", not "Uploading"). `performPinnedRequest` must send a `User-Agent` - catbox resets the socket without one, which made every catbox-hosted profile image fail to resize with a 503. `ImageEditorModal` (the "Resize / crop" dialog) is the same re-encode with a crop and an orientation on top; its "Resize to" fields are the resize, since the crop box only chooses which pixels survive. It keeps its own undo stack and swallows Ctrl+Z/Ctrl+Y in the capture phase whether or not it has a step to undo, because the editor behind it undoes document text on the browser's native stack and there is no way to put that back. Selected text in the visual surface is washed rather than inverted (`.bbcode-editor-surface ::selection`, background only): the colour and hue-shift controls act on a selection, so the OS highlight painting over it hid the very thing being adjusted. `[imagemap]` replaces an image rather than decorating one - it carries its own image URL and its areas, and osu! renders no `[img]` inside it - so in the visual pane the tool converts the image you picked (toolbar button or "Make imagemap" on its context menu) and seeds one draggable area; right-clicking a map adds or deletes an area, converts back to a plain `[img]`, or deletes it. In code mode the same button still inserts the raw template. Anything that reads staged images out of the document must go through `src/lib/bbcode-pending-images.ts`: a blob URL can now sit on an imagemap's first line as well as inside `[img]`, and missing one is a hard copy error rather than permission to silently omit the image. Copy reserves the clipboard during deferred uploads with a promise-backed `ClipboardItem`; once hosting succeeds the status changes from Uploading to Copying, and a stalled or rejected reservation gets one direct `writeText` fallback before the editor asks for an immediate retry.

Pending blob matching must accept bracketed IPv6 origins such as `blob:http://[::1]:3000/...`; Vite can serve local development on `::1`, and treating `[` as a BBCode boundary makes every newly pasted local image invisible to Copy BBCode.
