# Admin Surfaces

Deep reference for admin tooling: pack grants, ghost overlay, admin todos, translation reports, analytics, BBCode image audit. Admin controls are exposed through the frontend at `/admin/live-backend` and backend `/api/admin/*` (status, ingest fixtures, roster refresh, pause/resume country, set status/tier, delete country). Be careful with destructive controls.

## Purging a banned tracked player

The Users card on `/admin/live-backend` holds two controls. The reversible one is the soft deactivate/reactivate (`POST /api/admin/set-user-active`): it untracks the player, flips `users.is_active` to 0 and drops their queued jobs, and deletes nothing. The other one is the purge (`live-backend/src/users.ts`), and it is only for a tracked player who was banned or deleted on osu! and still shows up on the site.

The purge is not an account deletion and refuses to pretend to be one. Everything is keyed on the inactive `users` row, which stays behind on purpose as a durable suppression tombstone: `is_active = 0` with `profile_json.reason` set to the permanent-wipe marker. That row is what stops the player coming back, and it is read by the score ingestor (before any raw event, metadata or activity write), by the worker loop (any job whose payload names that user is skipped, plus a re-check after the osu! call in `enrich_user`), by the roster refresh (the users upsert, the roster row and the rank snapshot are all conditional on it), and by the profile reader (a cold mint throws `ProfileUserSuppressedError`, which the route answers as a 404 like any missing profile). `reactivateUser` refuses a permanently purged id with `PermanentlyWipedUserError`, so the reversible toggle cannot undo the irreversible control.

Targeting goes through a preview first (`POST /api/admin/wipe-user-preview`). Plain text resolves as a username even when it is all digits, because numeric osu! usernames exist and used to be read as ids; `#123` or `id:123` forces the id, and two stored accounts sharing a username come back as `ambiguous_username` rather than a guess. The preview returns the exact username, the immutable id, the avatar and what would be removed, and the destructive call (`POST /api/admin/wipe-user-data`) takes only that id plus the previewed username and a `WIPE <id>` confirmation, so a rename between the two steps is a 409 instead of a wrong purge.

It refuses any account with login-owned data (goals, wallets, holdings they own, skins, uploaded replays, replay-skin settings, signatures, map collections and favourites, Discord links, communities and reports, GOAT votes, translation and bug reports). Those are a person's own records, not tracking output, and deleting them is a different job.

What it does delete is every tracking-derived row and public appearance: raw `score_events` and the matching `live_event_log` entries, rank snapshots, snipe boards and `snipe_events`, top-score and `top_play_events` rows, all four maps projections, farm-helper stats/feedback/push targets, skill ratings and baseline, the profile snapshot and section cache, the whole `player_activity_*` set, the maniacards of that player wherever they are held (including other collectors' showcase slots, with the affected owners marked for a roll-up rebuild) and the pending jobs that name them. The deletes run as one `execBatch`, which is a single transaction, so a failure mid-purge leaves nothing half-removed; the shared derivatives that follow (the global farmed reconcile, the compact `country_maps_snapshots` scrub, the in-process cache clears) only repair rows other players share. Read paths that could still surface a retained row filter on the tombstone as well: tracker, snipes, top plays, skill leaderboards, rankings and the pack-card readers.

Left alone deliberately: GOAT poll nominations, since that board is meant to hold banned and deleted players, and another account's Discord tracker row pointed at them, which can never fire again once ingest drops their scores.

## Ghost overlay

`/admin/ghost` is the owner's ghost overlay: a Deltarune sprite driven around a visitor's screen, able to speak in a typewriter bubble, hold a pose, and run one-shot actions. It is page-scoped, and the audience is everyone on that route, one signed-in viewer picked off the presence roster, or nobody; the owner always sees his own ghost. The control stage frames the real page in an iframe at the watched viewer's viewport size, and the framed copy stays asleep via a `#ghost-preview` hash so it neither joins the roster nor draws a second sprite. Backend state is `live-backend/src/live/ghost.ts` (`GhostHub`, in-memory, serving process only, nothing durable, gated by `ENABLE_GHOST`); the visitor overlay is `src/components/ghost/`, mounted once from `__root.tsx`.

- Characters (Ralsei, Starwalker, Annoying Dog) are defined in `GHOST_CHARACTERS` in `src/lib/ghost-shared.ts`, the only place a new one has to be added: atlas, frame size, feet anchor, clip table, per-clip pixel bounds (hitbox and bubble lift come off the drawing, not the mostly-transparent frame), walk mapping, poses, actions, size range. Size on the wire is raw sprite pixels, so ranges differ per character and the backend clamps to 1..12. Unknown character ids and unknown clip names resolve to that character's default rather than a missing atlas row.
- Atlas URLs carry a per-character `atlas.version` because the service worker caches `/images/*` forever; tests pin each file's hash and grid, so changing art without bumping the version fails.
- The Starwalker and dog atlases are packed by `scripts/dev/pack-ghost-atlas.py`, a by-hand dev script needing Pillow and a local DELTARUNE install. Its header is the record of which sprites and frames each row came from and of the sheet-damage repairs; read it there rather than duplicating it here.
- Endpoints (deliberately bland `updates` paths on the wire: nothing a visitor's devtools shows may read like spying or hint the overlay exists): `GET /api/updates/stream?route=` (public SSE, one per page open, own budget via `GHOST_MAX_CLIENTS` / `GHOST_MAX_CLIENTS_PER_IP`, never the live-feed one; also the presence roster), `POST /api/updates/ticket` (admin-token gated, `getGhostControlTicket` in `src/lib/ghost.ts`), `POST /api/updates/control?ticket=` (driven from the browser at ~15 Hz so movement never pays for a hop through the frontend server), `GET /api/updates/presence?ticket=` (per-route counts capped at 40 routes, identities for signed-in viewers capped at 120), `POST /api/updates/say` (viewer replies, connection id from their own `hello` event, 6 per 30s, control characters stripped so a reply cannot forge an SSE frame), `GET /api/updates/inbox?ticket=` (replies, 40-entry in-memory ring, never SQLite).
- Viewer identity is a frontend-signed HMAC of `ghost:<id>:<username>:<expiry>` keyed with `LIVE_ADMIN_TOKEN` (`getGhostViewerTicket`), so aiming at one person cannot be spoofed via query string; an unsigned connection is anonymous and only ever sees an everyone-audience ghost.
- Route folding (lowercased pathname, no query or hash, no trailing slash, optional `/*` section wildcard) is duplicated on both sides and held together by tests. Broadcasts index clients by route, so a 15 Hz tick on an exact route only touches that page's connections.
- A line and an action stay on the session until replaced, so a late arrival still reads the current bubble; the overlay remembers what it has already shown a visitor (keyed by id and content) so a reload does not re-type a read bubble or re-fire the last action. Ending is ordered: `op: "end"` queues behind in-flight control patches (a patch overtaking its end would silently recreate the session), a disconnect with no route closes every session at once, and the hub sweeps idle sessions on a 10-minute window even with the panel gone.

## Collections (pack grants)

`/admin/collections` is the grant desk for the pack economy: pick a collector, hand them shards, mint them a card with every field on it chosen by hand, or take one back. Backend module `live-backend/src/features/pack-admin.ts` over four `LIVE_ADMIN_TOKEN` routes (`GET /api/admin/packs/collection` plus `POST .../collection/{wallet,grant,remove}`, handled in `http/routes/pack-admin.ts` and dispatched from `routes/admin.ts`); frontend server fns are `src/lib/admin-collections.ts`, gated with `requireTrueAdminAccess` rather than the wider `requireAdminAccess` every other admin page takes, since local dev should not be able to write shards into somebody's account. The form's pure half (`src/lib/admin-collections-form.ts`) is where the "blank means keep" rules live and is tested.

Two fields are special to this desk: an admin-granted `eternal` tier (above World Class and off the `cardPower` ladder; the separate completion reward is described in `docs/packs.md`) and Background art, the image a holding floats in place of its tier's triangles or starfield. Both are per holding, so granting either personalises one collector's copy without touching anyone else's; see `docs/packs.md` for how the motif reaches all three renderers and why its image is served through `/api/card-motif` rather than hotlinked. Background art keeps the same three states the skills snapshot has, so editing a copy count cannot silently strip a card's art.

The page opens in Simple, which is the whole job in four controls (pick a collector, give shards, pick a player, grant), with Everything holding the long tail of fields a holding can carry. Who is on screen lives in the URL (`?user=`, plus `page`, `q`, `mode`), so a refresh returns to the same collector and one can be linked to; the recent-collectors row under the picker is `src/lib/recent-players.ts`, the farm helper's list extracted and keyed per surface. Picking the card's player rates them there and then, through the same `computeManiaSkills` pass the reveal runs, so the ordinary grant is two clicks and still mints the card a real pull would have.

The whole point of the page is that it is not the game, so it deliberately writes what it is told: it can set a tier downward (the mint path only ever upgrades), award GOAT to anyone (the honorary roster guard exists because a stranger's `tier: "goat"` is a 500-shard printer, not because the owner cannot be trusted), backdate the pull stamps, force a serial, and repaint a `pack_cards` face that is otherwise first-write-wins. That last one is shared by every collector of that variant and is off unless the checkbox is ticked.

The tier label is the one field of the face a single collector holds privately, because naming one person's card ("a GOAT that reads *manolo*") is the point and renaming it on every other holder's shelf is not. `pack_collection_cards.tier_label` is that override, only this page writes it, and it is what the card art prints: it reaches `labelOverride` on `buildManiaCardRenderDataFromSkills`, the same slot an honorary player's `cardTierLabel` uses, and beats it. Every surface that draws a stored card passes it (collection tiles, spotlight, album, the showcase, the `/pull` page and its OG image), and the thumbnail cache key already hashes `tierStyle.label`, so a relabelled card re-renders on its own.

The rule is deliberately dumb: the form sends a label only when one was typed, an empty box clears the override, and an absent one leaves what the holding had. The tier's own name is never stored, because storing it would be indistinguishable from someone typing it and would then beat an honorary player's label. A variant this page creates is left unlabelled in the catalog for the same reason. `customLabel` on the wire is that column alone, while `tierLabel` stays the coalesced display value. Note both tables carry `tier_label` now and a duplicate result column resolves to the *first*, so any new join must alias the catalog's (`catalog_tier_label`) rather than letting it shadow - the test helpers hit exactly this. What it cannot do is fake community history: a grant writes no `pack_pull_events` row, so it never shows up in the `/packs` pull ticker as something that was pulled, and it books no `pack_game_rewards` row, so it never eats into anyone's daily arcade allowance. Wallet writes still go through `setPackWalletEconomy` in `pack-wallets.ts`, keeping every write to a wallet's numbers in the one module. "Fill from their plays" runs the real `computeManiaSkills` pass over the player's stored best scores in the browser, so a hand-granted card can be made to read exactly like a dealt one before it is edited. Removal drops the ownership row outright rather than zeroing its copies (a zero-copy row would still shadow a later pull's `first_pulled_at`) and takes its showcase slot with it; the `pack_card_serials` row is left alone unless the checkbox asks, since an orphaned serial is invisible and a re-grant picks the same number back up, while deleting a card's highest serial lowers the "of N" every other collector of it reads.

Removing an Eternal has one extra effect: when it was the collector's last Eternal holding, the removal transaction also clears their completion-reward claim. Recycling never does this. If they still satisfy the current pack pool and GOAT roster, their next pack can therefore restore the card; removing one Eternal while another variant remains keeps the claim closed.

## Admin todos

`/admin/todos` is the owner's private todo list, backed by `features/admin-todos.ts` (durable `admin_todos` table, single user, no per-user scoping) over `GET /api/admin/todos` + `POST /api/admin/todos/{create,update,delete,clear-done}`. Frontend server fns in `src/lib/admin-todos.ts` proxy with the shared admin token; the nav entry and page are `canUseAdminFeatures`-gated.

## Translation reports

`/admin/translation-reports` is where reader feedback about the site's own translations lands. A visitor browsing in a non-English locale gets a "Report a translation" control under the language picker in the settings panel's Appearance tab (`src/components/settings/TranslationReportForm.tsx`, hidden in English since the source strings are written in it), and files what reads wrong, what it should say, and anything else.

No login is required: the people who catch a bad translation are the ones reading in that language, signed in or not. `features/translation-reports.ts` owns the durable `translation_reports` table (never pruned by retention) and the two ceilings that open write path needs: a daily per-reporter cap keyed on an opaque `reporter_key` (`user:<id>`, or the visitor's address HMACed with the bridge secret, never stored raw), with a much larger shared ceiling for the anonymous bucket that deployments without trusted proxy headers collapse into, plus a 24h duplicate guard that returns the stored row instead of a second copy. The submit route is bridge-gated (`POST /api/translation-reports/submit`, see `docs/backend.md`); reading and triage are admin-token gated: `GET /api/admin/translation-reports` + `POST /api/admin/translation-reports/{update,delete,clear-reviewed}`, proxied by `src/lib/translation-reports.ts`. A non-duplicate report also pings the owner's Discord channel (`translationReportEmbed` through `postOwnerNotice`, the same `DISCORD_BUG_REPORT_CHANNEL_ID` bug reports use), after the browser has its answer and never blocking it.

A report is `new`, `resolved` or `dismissed`; nothing here edits a catalog, since fixing a string means editing `src/locales/<locale>/messages.po` and recompiling. The board keeps the reporter's words verbatim and adds only what finds the string again: locale, the page path they were on (query string stripped), and their osu! account when they had one.

## Bug reports

`/admin/bug-reports` is where players' reports about broken things land. Anyone can file one from `/report` (footer link, nav entry), signed in or not: whoever hit the bug is the person worth hearing from, and most people find one before they ever log in.

A report carries what the reporter wrote plus what nobody should have to type: the page they were on (query string stripped), user agent, viewport, locale, country scope, and the newest changelog date standing in for a build id. That block is collected by `src/lib/bug-report-context.ts` and shown to the reporter in full before the send. Up to three screenshots can ride along.

`features/bug-reports.ts` owns the durable `bug_reports` table (never pruned by retention) and the same two ceilings the translation reports use: a daily per-reporter cap keyed on an opaque `reporter_key` (`user:<id>`, or the visitor's address HMACed with the bridge secret, never stored raw), a much larger shared ceiling for the anonymous bucket, and a 24h duplicate guard that returns the stored row instead of a second copy. The write side is bridge-gated (`POST /api/bug-reports/{submit,authorize-screenshot,attach,reply}`, `GET /api/bug-reports/{mine,screenshots}`, see `docs/backend.md`); triage is admin-token gated: `GET /api/admin/bug-reports`, `GET /api/admin/bug-reports/get`, `POST /api/admin/bug-reports/{update,reply,edit-message,delete,clear-closed,promote-to-todo}`, proxied by `src/lib/bug-reports.ts`.

A report is `new`, `investigating`, `fixed`, `wontfix`, `duplicate` or `notabug`. `notabug` is the tier for what arrives through /report without being broken - a question or a feature request - so it is not a closed status: nothing there is stamped `resolved_at`, and "Clear closed" (fixed + wontfix + duplicate) leaves it alone. Reporters never see it: `toBugReportForReporter` reports it back as `new`, so a question or suggestion reads as still open on /report rather than as a rejection. `admin_note` is private triage scratch; the public conversation lives in `bug_report_messages`, beginning after the original `bug_reports.body`. It is append-only apart from one correction: the owner can edit their own message in place from the board (`edit-message`), which stamps `edited_at`, shows an "edited" mark on the admin card, and re-points the compatibility `reply` mirror when the edited row is the newest admin message. A reporter's words are never editable. Existing values from the old mutable `reply` column are backfilled once as admin messages, while that column continues to mirror the newest admin message for rolling-deploy compatibility. Only a signed-in reporter has a verified thread owner, so anonymous reports remain one-way and the board hides their Reply control. A reporter follow-up is owner-checked, capped at 30 messages per report per day, and never changes triage status; only the admin board can reopen a report. It still updates activity time, keeping the newest conversation first within its current status view. Both `/report` and the admin card present follow-ups as compact left/right bubbles, start on the newest six, and bound expanded history in their own scroll areas. "Make a todo" creates an ordinary `admin_todos` row in the `bug` category and stores its id on the report, so one work queue stays one queue and a report cannot be promoted twice.

Screenshots go to the private `mania-hub-replay-cache` bucket under `bug-reports/<id>/<n>.<ext>`, never the public CDN: a screenshot of a bug holds whatever else was on that screen, and the site is not an image host. The browser uploads to the frontend route `/api/bug-report-upload` (`src/lib/bug-report-upload-server.ts`) against the ticket the submit minted, which is the credential the way a skin upload's ticket is; the bytes are capped at 5 MB and typed by magic bytes, and the key shape is checked again by the backend before it is recorded, so a ticket holder cannot point a report at some other object in the bucket. Reads are short-lived signed URLs handed out only to an admin or the reporter themselves (`getBugReportScreenshotUrls`). Deleting a report or clearing the closed ones removes the objects too.

With `DISCORD_BUG_REPORT_CHANNEL_ID` set, each new report also posts an embed to that one channel through `postOwnerNotice`. Deliberately not a subscribable feed: a report can quote whoever filed it, so it goes where the owner put it and never fans out to community servers. The post is best effort and never blocks the reply to the browser. The same channel carries the other two owner notices: a new translation report, and a Discord server landing in the `/communities` review queue (see below). The env var keeps its bug-report name so a deployment does not have to move.

## Analytics

`live-backend/src/features/analytics.ts` is the site's only analytics store; there is no third-party fallback. The frontend `/api/sync` proxy writes every tracked event to `POST /api/analytics/capture` (bearer-token gated, stamped with the edge GeoIP country and a bot verdict). Events land in a separate SQLite file (`ANALYTICS_DATABASE_URL`, default `data/mania-hub-analytics.db`, own WAL) through a 1s-batched writer; retention self-prunes hourly (`ANALYTICS_RETENTION_DAYS`, default 90). Both admin surfaces require `LIVE_BACKEND_URL` + `LIVE_ADMIN_TOKEN`. Read side:

- `GET /api/admin/analytics/monitor`: the `/admin/live-backend` analytics tab, polled at 5s (KPIs, a traffic timeline of up to 48 buckets, the recent-event feed, aggregate cards). Ranges of 48h and up answer from hourly rollup tables (`analytics_hourly_*`, advanced every 30 minutes for hours at least 25h old, since capture clamps client timestamps 24h back) plus a raw tail, so a 30-day read costs the same order as a 24-hour one instead of scanning the whole events file; per-visitor hour rows exist because distinct counts (unique visitors, countries, referrers, timeline buckets) cannot be summed from totals. While the rollups are behind (first boot after the deploy that introduced them, or a long outage) those ranges fall back to the old full scan on a worker thread with its 300s timeout. Timeline buckets widen to whole hours on the rollup path, so the bucket count can come out just under 48 and the newest bucket can end past "now"; the chart renders whatever length it gets.
- `GET /api/admin/analytics/viewers`: the signed-in roster, backed by the durable `analytics_viewers` table, which is upserted on flush and survives event pruning so it answers "who has ever signed in". `?sort=recent|pp|rank` orders it; pp/rank are read out of the main DB's `users` table per viewer id (`features/analytics-viewer-ranks.ts`) since the two live in separate SQLite files, and that sort scans the whole roster before slicing to `limit` so the top is the real top. A viewer the backend has never ingested comes back `pp: null` and sorts last. `?country=XX` filters in SQL, so a country's page reaches players older than an unfiltered page's cut; the response carries `matched` plus `countries` for the filter's own list.
- `GET /api/admin/analytics/viewer-events?viewerId=`: one player's trail, fetched only when a roster row is expanded, off a partial expression index on the events table's `viewer_id` prop, newest first, bots and the player's own `/admin/` browsing excluded. The roster is durable and events are not, so an empty answer means retention rather than failure.
- `GET /api/admin/analytics/event-catalog` and `GET /api/admin/analytics/event-lookup?event=&sinceTs=&limit=`: the analytics tab's Lookup view, which reads the feed backwards - pick an event name and see who fired it, newest first. The catalog is one group-by over the `(event, ts)` index (index-only, so bots are counted in a name's total even though the lookup itself drops them) held for 30s. The lookup answers both readings in one call: `people` folds the newest `EVENT_ACTOR_SCAN_ROWS` firings to one row per person (signed-in visitors group by osu! id, so one player on two devices is one row; everyone else groups by device), `occurrences` leaves every firing in the feed's row shape. Bots and `/admin/` browsing are excluded from both; `sinceTs` is optional and the view defaults to the whole retention window rather than the range selector.
- `GET /api/admin/analytics/valley`: the `/valley` villager layer.
- `GET /api/admin/analytics/live`: realtime SSE, authenticated by short-lived tickets from `POST /api/admin/analytics/live-ticket`.

## Dynamic renders

`/admin/dynamic-renders` combines signature-background moderation with an on-demand player preview. The preview search calls the normal live-backend profile `/snapshot` route so an explicit admin lookup can warm a player Mania Hub has never stored, then draws every layout for the selected type through the same `/api/signature-preview` endpoint the player editor uses. Supplying a target player to that endpoint is accepted only when the signed session has `canUseAdminFeatures`; ordinary users remain locked to their own osu! id. Preview renders use the type's default style, write no signature settings or R2 image, and return `private, no-store` PNGs.

## BBCode image audit

`/admin/bbcode-images` is the narrower tool for the `bbcode/` prefix, whose objects are permanent, have no second copy, and are tracked by nothing but their own `uploaded-by` metadata. `src/lib/bbcode-image-audit.ts` lists the prefix, reads each uploader's profile BBCode fresh from osu! (`page.raw`, deliberately uncached), and reports each file as on a profile / unused / unchecked. Two rules make it safe to delete from: a file counts as used if *any* read profile embeds it, since content-addressing means one object can be shared and `uploaded-by` names only the last uploader; and a profile that could not be read yields `unchecked`, never `unused`. `deleteUnusedBbcodeImages` re-runs the whole audit server-side and drops only what is still unused, so the client never labels its own deletions.

## Leaderboard imports

The **Import a leaderboard** panel inside a profile's "Add a missing score" dialog is shown to `canUseAdminFeatures` sessions only. It searches the site's map index as typed, like `/maps` (ranked or loved, the same token syntax such as `key=6`, sorted by plays, stars or ranked date, either direction) and queues a chart's global top 50 for the ordinary ingest, one job per chart; the rows show queued / importing / done with the stored count as the jobs run. Players from untracked countries are counted, not stored; nothing here bypasses the ingest's gates or rates anything. Details in `docs/features.md` under dan estimates.
