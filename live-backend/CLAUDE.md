# Live Backend

Architecture guide for the always-on `live-backend/` service. Paths below are relative to `live-backend/`. Fuller detail on demand: `../docs/backend.md` (jobs, HTTP surface, retention), `../docs/features.md`, `../docs/packs.md`, `../docs/discord.md`, `../docs/admin.md`.

The live backend is the source of truth for live surfaces when `VITE_LIVE_BACKEND_URL` is set. Browsers fetch a snapshot on page entry, then subscribe to SSE (`/api/live?country=XX`) for deltas; SSE is one-way and browsers never talk to oSC. Reconnects replay missed events via `Last-Event-ID` against `live_event_log`.

Ingest flow (`src/ingest/score-ingestor.ts`):
1. Scores arrive from three sources. The osu! API recent-scores poller (`src/osc/scores-fallback.ts`) is the de facto ingest path today, and the admin monitor labels it "Ingest"; the legacy oSC Socket.IO client (`src/osc/client.ts`) and its JSON backfill (`src/osc/backfill.ts`) sit behind it, and the poller is gated on socket staleness in code, so do not describe the socket as alive in UI copy.
2. Filter to mania; detect country via `country_rosters` (oSC payloads lack country).
3. Raw rows land in `score_events`; metadata upserts into `users` / `beatmaps` / `beatmapsets`; projections and follow-up jobs fan out per enabled feature tier.

Job queue (`src/jobs/queue.ts` + `src/workers.ts`): jobs table with priority, dedupe keys, per-type backoff, and pressure shedding (low-priority types defer when queue depth is high). Workers run in dedicated lanes (fast enrichment, osc-backfill, osc-country-catchup, maps-refresh, dan-estimates, activity-analysis incl. chart analysis, snipe-seed, replay-video render, replay-video finalize, and more). Job types (user/beatmap enrichment, roster + top-score + maps refreshes, snipe seeding, activity and dan analysis, oSC catch-up, replay-video render/export) are enumerated in `../docs/backend.md`.

Feature modules (`src/features/`), one per surface (full per-feature models in `../docs/features.md`; packs, streak/blitz and the GOAT poll in `../docs/packs.md`):
- `tracker.ts`: live score timeline with filters.
- `top-plays.ts`: confirms a candidate score entered the player's top plays via osu! API; records PP gain in `top_play_events`.
- `snipes.ts`: per-beatmap/lane boards in `country_beatmap_scores`; an overtake writes `snipe_events`.
- `maps.ts`: aggregates roster users' farmed scores into `country_maps_snapshots` (plus a global rollup).
- `farm-helper.ts` + `farm-helper-key-stats.ts`: PP-gain recommendations from a player's top 200 vs a global peer pool at similar PP; per-keymode weighted PP in `farm_helper_user_key_stats`.
- `activity.ts`: per-day player skill vectors (stream/jack/LN/etc.) in `player_activity_*`, bucketed in the player's country timezone at read time.
- `dan-estimates.ts`: cached dan ratings (`dan_estimates`), small batches inline, larger ones queued.
- `global-rankings.ts`, `rank-snapshots.ts`, `player-profiles.ts`: global ranking snapshot (union of tracked rosters by pp), 7-day rank deltas, and cached profile snapshots.
- `user-map-collections.ts`: the collections players build and post themselves, the community half of the `/maps` Collections tab (`user_map_collections`, `user_map_collection_items`, `user_map_collection_favourites`; routes `/api/map-collections/*`, bridge-gated including the reads). Nothing reviews a posted collection: it holds beatmap ids and nothing else, and each of those already passed osu!'s own moderation before it could reach `map_search_index`, which is also what every write validates membership against. The keymode chip, the member count and the cover collage are derived from the members on each write rather than typed by the author, an edit that omits `beatmapIds` leaves the list alone, and the like count is denormalized onto the row but recomputed from the favourites table in the same batch. Owner writes, plus `asAdmin` for a takedown; neither table is pruned by retention. The auto packs beside it are `map-collections.ts` and share nothing but the tab.
- `goals.ts`: per-user goals (`user_goals`) that auto-complete off the score pipeline; backs `/goals`.
- `my-data.ts`: the signed-in player's dashboard projections (reads existing projections, owns no table); backs `/my-data`.
- `player-skills.ts`: Etterna-style per-keymode skillset ratings from the player's top plays (per-play MinaCalc SSRs at the played rate, `player_skill_ratings`); backs the my-stats "Skill rating" card.
- `pack-wallets.ts`: synced maniacard pack economy (`pack_wallets`, `pack_collection_cards`); backs `/packs`. For signed-in accounts the economy is server-owned: the draw route (`pack-draw.ts`) spends charges/shards and writes the dealt copies itself, grants go through `addWalletShards`, wallet pushes are compat no-ops, and the only client-authored economy ever believed is the one-time, capped first-sync merge of a pre-login local wallet (`mergeImportedPackWallet`). An ownership row holds only that holding's state; the card's identity lives once per variant in `pack_cards` and its mint skills snapshot is interned in `pack_card_skills`, so a card held by a thousand collectors stores its face once while each of them keeps the exact snapshot their own pull froze.
- `pack-community.ts`: the public read of the economy behind `/packs/collections` (`GET /api/packs/community/*`), including the showcase wall (`pack_showcase_cards`, the cards a collector picked to show; the write stays owner-scoped on `/api/pack-collection/{id}/showcase`). Reads nothing of its own: it groups `pack_collection_cards` by collector instead of filtering it to one, and every board, the directory and a collector's rank are sorted out of that in JS. Two cached snapshots with different lifetimes (collectors 2 minutes, cards 30), both stale-while-revalidate, plus a third much cheaper read for the header's totals (`buildPackCommunityTotals`, 20 seconds, a few sums over the roll-up tables and the `pack_wallets` opened-packs sum). `computedAt` on the stats response is the totals' clock, since that is what the page counts live pulls on top of. What the page costs is decided by three things, not by the boards: the counts are maintained rather than regrouped (`pack-community-rollups.ts`, triggers on `pack_collection_cards` into `pack_community_dirty_*`, reconciled owner-scoped into `pack_community_{owner,owner_tier,card}_stats`, with the old full scans kept as the fallback for a roll-up that is missing, untriggered or a generation behind); a build runs on its own worker thread (`pack-community-thread.ts`, the maps-snapshot-thread pattern) because local libsql is synchronous and a scan on the loop stops the whole process; and the last good snapshot is written next to the database (`pack-community-*-v1.json.gz`) so a restart starts warm. The thread is also the one writer of the roll-up tables. `ensurePackCommunityRollupTriggers` runs from the boot path rather than the migration, after the two rebuilds that drop and rename `pack_collection_cards`. The per-collector pool ratio is asked backwards, counting the cards that fell *out* of the pool, because that set is a tenth the size. See `../docs/packs.md` for the measurements behind all of it, including the 25s page load that prompted them.
- `pack-admin.ts`: the owner's grant desk behind `/admin/collections` (`http/routes/pack-admin.ts`, admin-token gated). The one caller allowed to write a holding directly: any tier including a GOAT off the roster, a tier the mint path could only upgrade to, backdated pull stamps, a forced serial, and a repaint of the shared `pack_cards` face. Those guards are about a stranger on the wire, not about the owner. It still writes no `pack_pull_events` row (a granted card is not a pull the community feed should claim happened) and no `pack_game_rewards` row (a grant spends nobody's daily arcade allowance), and wallet numbers go through `setPackWalletEconomy` in `pack-wallets.ts` so every economy write stays in that module.
- `pack-games.ts` + `pack-streak.ts`: the card arcade. `pack-games.ts` is the shared till that pays both modes of the `/streak` game, capped per account per day in `pack_game_rewards`. For casual streaks the cap is the security model, not the scoring: a run is scored off data the client can read for itself. Blitz streaks are dealt and scored here instead (`pack-streak.ts`, `pack_streak_runs`) because they feed a public leaderboard: the server holds the face-down card's number and only counts a guess that beat `deadline_at`. The board itself reads `pack_streak_bests` (one durable row per account per pool, never pruned), so the run log stays transient and is pruned on the ordinary retention schedule. Records only leave the board by admin removal (`POST /api/admin/packs/streak/remove`, driven from a true-admin-only control on the board itself), which deletes the record and that account's ended runs in the pool but bans nobody.
- `goat-poll.ts`: a time-boxed community poll on `/packs` for who joins the honorary GOAT roster (`goat_poll_nominees`, `goat_poll_votes`). Public net score (`up - down`), sorted on; banned/deleted accounts are nominatable with a `web.archive.org` proof, whose archived URL supplies the osu! id that keeps one player to one row. Nothing is capped per account: the write routes take the admin-token bridge (so the per-IP guard does not apply) and the ceilings are structural instead — an osu! login behind every write, the unique indexes that keep one player to one row, the vote primary key that keeps one voice per account per row, and an admin's delete key. Every write publishes a country-less `goat_poll` SSE event carrying the changed row, so open boards patch on the click rather than on their 20s backstop poll. Two true-admin-only routes sit under `/api/admin/goat-poll/`: `remove` (a delete key for a joke nomination, not a ban) and `voters` (the ballot behind one row, never on the public board). The `GOAT_POLL` constant at the top of the module is the whole switch (`enabled`/`adminOnly`/`id`/`opensAt`/`closesAt`), hardcoded rather than env so a poll ships with a deploy instead of a VPS `.env` edit; `enabled: false` 404s every route and hides the widget, `adminOnly: true` 404s the same way for everyone but an admin, whose admin-ness the frontend vouches for per request since the shared token cannot, and `id` scopes a rerun. Dates must be explicit UTC instants (anything `Date.parse` would read as local time is refused, which switches the poll off); the board ships `serverNow` so browsers count down against the backend's clock rather than their own. Neither table is pruned by retention. Nothing promotes a winner by code — the roster is edited by hand.
- `analytics.ts`: in-house web analytics, the site's only analytics store. Events arrive from the frontend `/api/sync` proxy at `POST /api/analytics/capture` (bearer-token gated) and land in a **separate SQLite file** (`ANALYTICS_DATABASE_URL`, own WAL) via a 1s-batched writer; admin queries at `/api/admin/analytics/{monitor,valley,viewers,viewer-events,event-catalog,event-lookup}` power the `/admin/live-backend` analytics tab and `/valley` (`viewer-events` is one player's own trail, read on demand when a roster row is expanded; `event-lookup` is the inverse, one event name and who fired it, behind the tab's Lookup view); `analytics_viewers` is a durable roster of every osu! account that has browsed while signed in (upserted on flush, backfilled once from stored events) and deliberately outlives event pruning; `/api/admin/analytics/live` streams accepted events over SSE (short-lived tickets from `/live-ticket`, since EventSource can't send auth headers). Monitor ranges of 48h+ read hourly rollup tables (`analytics_hourly_*`, advanced every 30 min for hours older than the 25h capture-clamp grace) plus a bounded raw tail, so long ranges stay cheap as the events file grows; mid-backfill they fall back to the old full scan on a worker thread. Hourly self-pruning (`ANALYTICS_RETENTION_DAYS`, default 90) covers the rollups too. Owned by the HTTP-serving process; the pure worker role never opens it.

- `uploaded-replays.ts`: the owner index for `.osr` files uploaded on `/replay` (`uploaded_replays`). The file lives in the frontend's R2 bucket and names no uploader, so this table is what backs "Your uploads" and what authorizes a delete; the routes only ever touch the row, and the caller deletes the objects. Never pruned by retention.
- `communities.ts`: the `/communities` directory of osu!mania Discord servers (`discord_communities`). Nothing publishes on submit: a row is born `pending` and a moderator approves it, an owner's later edit stays live but raises `edited_since_review` for the review page, and a rejected listing its owner edits goes back to pending. The review routes sit under `/api/communities/` rather than `/api/admin/`, because reviewing is a hand-kept per-feature moderator list reached from the directory itself, not an admin surface. The listing's identity comes from Discord's unauthenticated invite endpoint (`discord/invites.ts`, standalone so it survives `ENABLE_DISCORD_BOT=false`) rather than the form, and ownership was proved by Discord OAuth on the frontend; `toCommunitySummary` is the only row-to-wire converter, so the review fields and the submitter's Discord account cannot leak onto a public card. A listing that named the places it is for withholds its invite and its `guildId` from everyone else (`widget.json` turns a guild id into an invite for any server with its widget on) but keeps its icon and banner, pointed at the frontend's `/api/community-image` instead of at the CDN paths that carry that id; the frontend route resolves it through `GET /api/communities/image-url`, gated by the same `communityVisibleTo` the page uses, and pipes back only the bytes. `communities/refresh.ts` re-resolves approved invites every 6 hours beside retention (no osu! API budget), hiding a listing after `COMMUNITY_INVITE_FAIL_LIMIT` real failures while leaving it visible to its owner. `POST /api/communities/preview` resolves an invite without writing anything, so the submit form can show the real server and refuse a bad link while it is still being typed; with an empty invite it tries the guild's own `widget.json` first (the only invite an OAuth app can find without a bot in the server), then checks whatever it found like any pasted one. Tags are owner-typed free text (`tags_json`, normalized to a charset with no quotes so the LIKE match cannot half-match a longer tag), and the list query returns country, language and tag facets (the last via `json_each`), so the page offers only values that have servers behind them. Anyone browsing can flag a listing (`POST /api/communities/report`, `discord_community_reports`): a report is a message to the moderators and to nobody else (never the owner, never a count on a card), one row per person per listing, capped per account by `COMMUNITY_MAX_OPEN_REPORTS_PER_USER`, and it rides `/api/communities/queue` as a third list so the review page shows a flagged listing once with its reports under it; every review decision resolves them. The directory is open to everyone, signed in or not, but every route including the reads still takes the admin-token bridge: the frontend server functions are the only callers and they forward the osu!-verified viewer id and country, which is what decides who gets a restricted listing's invite.

Discord bot (`src/discord/`): optional HTTP-interactions bot (maniabot), gated by `ENABLE_DISCORD_BOT` / `ENABLE_DISCORD_FEEDS`; slash commands plus per-channel subscription feeds, frontend `/discord` and `/admin/discord`. Replies are Components V2 and use custom application emojis for grade pills / mod icons (`discord/emojis.ts`, built by `scripts/build-discord-emojis.mjs`, uploaded via the admin "Register emojis" action, with plain-text fallbacks). Keep embeds free of decorative unicode emoji (enforced by `discord-embeds.test.ts`). Details in `../docs/discord.md`.

Admin ghost (`src/live/ghost.ts`, gated by `ENABLE_GHOST`): in-memory, serving-process-only sessions behind the owner's sprite overlay (Ralsei, Starwalker or the Annoying Dog; the character is an opaque string here, and the roster lives in `src/lib/ghost-shared.ts`). Every page open holds one `/api/updates/stream?route=` SSE connection on its own budget (`GHOST_MAX_CLIENTS`, `GHOST_MAX_CLIENTS_PER_IP`), which doubles as the presence roster; `/api/updates/{ticket,control,presence}` are the admin side, all routed ahead of `routeHttp` so 15 Hz movement never spends the page's public API budget. Viewer identity is a frontend-signed HMAC keyed with `LIVE_ADMIN_TOKEN`, so targeting one person is not spoofable. Viewers answer back through `/api/updates/say` (capability is the connection id, only valid while being shown the ghost) and the owner reads them on the `/api/updates/inbox` SSE stream. Nothing is durable: sessions and replies are in-memory, and a restart ends both. Full detail in `../docs/admin.md`.

HTTP (`src/http/`): `snapshots.ts` is the router (gates: origin check, media/discord pre-gate dispatch, per-IP rate buckets) plus a compat re-export façade; endpoint handlers live in `src/http/routes/` by domain (system, profiles, analytics, admin, user-data, snapshots, analysis, osu-proxy, packs, goat-poll, replay-video, skins), with shared plumbing in `context.ts` (HttpContext), `request.ts` (auth/body/params), `respond.ts` (JSON/CORS/rate-limit responses), `country-activation.ts`, `status-report.ts` (status/health bodies), `maps-response-cache.ts` (prepared-response caches + boot warmers), and `snapshot-queries.ts` (query parsers). Endpoints: snapshot, profile, dan-estimate, audio, replay-video, and country routes, plus admin routes under `/api/admin/*` gated by `LIVE_ADMIN_TOKEN` (full list in `../docs/backend.md`). Note: some per-user endpoints (goals, my-data, roster self opt-in/out, pack wallet/collection, the uploaded-replay owner index, skins ownership, communities, the GOAT poll's writes) plus the osu! proxies and analytics capture are gated by `isBridge` instead: called server-to-server, with the frontend injecting the token plus the osu!-verified viewer id so a user only touches their own data. `LIVE_BRIDGE_TOKEN` is that credential; while it is unset the bridge is the admin token (the old behaviour), and once it is set the admin token no longer opens those routes, so both sides move in one deploy. Bridge requests are not exempt from rate limiting like admin ones - they are charged the generous `bridge` bucket (`BRIDGE_RATE_PER_MINUTE`), since one address carries every signed-in visitor. Per-IP rate limiting via `src/http/abuse-guard.ts`; CORS from `ALLOWED_ORIGINS`.

Replay video: gated by `ENABLE_REPLAY_VIDEO` (default off; local-only — when off the job endpoint 404s, the worker lanes don't register, and playwright-core never loads). The browser renders/encodes MP4 with WebCodecs and uploads it, or the backend renders server-side in headless Chrome (`src/replay-video/server-render.ts`, playwright-core via dynamic import). Finalization muxes audio with ffmpeg and uploads to R2. Heavy deps (sharp, jszip, sanitize-html, @aws-sdk/client-s3, playwright-core) are lazy-imported at their point of use and must stay out of the boot module graphs (`npm run probe:boot-imports`, guarded by `tests/boot-imports.test.ts`). `scripts/dev/replay-video-job.ts` is a Vite dev middleware fallback when no live backend is configured.

Storage and retention: LibSQL/SQLite (default `live-backend/data/mania-hub-live.db`, WAL), schema in `migrations/001_initial.sql`, applied at boot. `src/retention.ts` runs hourly to prune raw/transient rows (score events, event log, done jobs, api logs, snapshots; per-table cutoffs in `../docs/backend.md`); durable projections (boards, events, users, beatmaps, rosters) are never cleaned up. DB size caps come from `MAX_LOCAL_DB_BYTES` / `TARGET_LOCAL_DB_BYTES` (prod currently 26/24 GiB; keep the max at or below ~26 GiB on the 75 GB disk so an in-place VACUUM — which needs ~2x the DB size free — stays possible).

osu! API budget: token-bucket limited in `src/osu/client.ts` (~45/min target, 60/min hard); calls are logged to `api_call_log`. Don't add new osu! API call paths without going through this client.
